## 1. Verdict

**PASS for the matrix as a gate, with one automatic step deliberately unsupported and resolved by disclosure.** Scenarios A, C, D and E pass. Scenario B passes its repair, backup, restart and no-op assertions; its prune assertion is not met by design, because the prune is deliberately not supported for profiles whose bundle declarations do not resolve.

Skill section 0.2 resolves exactly this case: a step the release does not perform automatically is acceptable when the version says so plainly and ships an executable manual recovery. The v0.4.8 release notes now do both at commit 8bc1b8fa3 - automatic pruning only when the profile's bundle declarations resolve, a CLI-created profile keeping the retired override on every route including a plugin-manager update, the composition staying correct with the repeated not-found line as the only symptom, and the two-line manual removal as the remedy - and that remedy was executed here (section 5.9): after removing the entry the same `--dump-config` exits 0 with zero stderr lines.

What this matrix does not claim: the prune does not run on CLI-created profiles, and no measurement here shows it doing so. What it does show is that the repair works, that the guard refuses to delete when declarations are unknown, that the prune deletes exactly the orphan when they resolve, and that the documented recovery clears the only symptom.

The finding this release carries, and how it was closed:

F1 (found on e6f336f01, repair half fixed by c404cb115, prune half resolved by disclosure at 8bc1b8fa3). **The row-name repair and the orphan prune were both gated on every dsh.profile.bundles entry being resolvable inside the profile's own node_modules, and a profile created by the official CLI never satisfies that.** Such a profile lists @deepseek-ai/dsh-base and @deepseek-ai/dsh-web-app in dsh.profile.bundles but does not install them (the CLI supplies them at boot). liveOverrideIds therefore returns undefined for the first bundle it cannot read, and pruneOrphanOverrides returns before it reaches the repair, silently: the job still settles done. On that shape the update path neither rewrites the stale row names nor prunes the retired override, and the user is left with dead overrides plus the loader line patch: entry "web-ui-model-capabilities" not found on every boot. Measured cause, both directions, in section 5.5. One code path serves all three update routes (gateway.ts:930, :1194 and :1629 all call the same pruneOrphanOverrides, whose first acts are liveOverrideIds and then the repair at :1864), so this is not specific to the CLI writer.

Status of the two halves on the shipped tree (dev c404cb115, measured in section 5.8):

- Repair: fixed. pruneOrphanOverrides now runs repairProfileRowNames() as its first statement, before the composition and live-id guards, so the update job rewrites the stale names on a CLI-created profile. The job keeps the pre-write bytes in one cordis.patch.yml.bak-plugin-manager, and a restart changes nothing.
- Prune: deliberately unsupported on that shape, and now disclosed as such. The guards are unchanged, so liveOverrideIds still returns undefined there and the prune deletes nothing: the retired override survives and the loader keeps reporting it. The safety property that makes the guard worth keeping - an unknown live-id set must never delete - is measured in both directions in section 5.8, and the release notes at 8bc1b8fa3 state the limitation and the manual removal, which section 5.9 then executed. That is the section 0.2 resolution for an automatic step a release does not support.

The startup path repairs the same rows independently (section 5.4 and 5.8), which is why a user who never opens the plugin manager still ends up with correct row names.

### 5.5 Cause, measured in both directions

The post-update pass starts at pruneOrphanOverrides (gateway.ts:1853), whose first two acts are composedEntryIdsOf(dump) and liveOverrideIds(composed). liveOverrideIds walks dsh.profile.bundles and returns undefined as soon as one bundle package.json cannot be read, because that bundle own row declarations are then unknown and nothing may be pruned. The same method, same arguments, on a profile that differs only in that the two SDK bundles are installed into its own node_modules (/tmp/dsh-verify-0_4_8-homeB2, profile upgradeV, 0.4.8 installed, same seeded layer):

The startup repair (index.ts:110) needs only the composition and is unaffected, which is why section 5.4 works.

### 5.6 The first attempt, and the six-minute CLI budget

The first attempt (job-1, with the profile restored to 0.4.7 afterwards) settled as a job error whose text is the captured CLI output, ending in the pnpm success line:

```
{"job":{"id":"job-1","action":"update","targetVersion":"0.4.8","phase":"error",
 "error":"[check] Lockfile passes supply-chain policies (verified 37s ago)\n...\nPackages: +22 -10\n...\nDone in 576ms using pnpm v11.9.0"}}
package.json after that attempt: "@linxin666/dsh-web-all": "0.4.8"
cordis.patch.yml: unchanged, no backup
```

In that quoted line the CLI's leading check glyph is written as [check], because this repository bans the code point in its own files; the rest of the line is the captured output verbatim.

The gateway kills the CLI child at ADD_TIMEOUT_MS = 6 * 60_000 (gateway.ts:31) and treats any non-zero return as a failed job with the captured output as the message. That the killed child produces a non-zero code rather than a success code is exactly what awaitCliExit does:

```
$ node --experimental-transform-types /tmp/dsh-verify-0_4_8-harness/await-cli-exit-probe.mjs
awaitCliExit(timeoutMs=1000) on "sleep 5" returned code = null | elapsed ms = 1002
code !== 0 interprets as failure: true
```
