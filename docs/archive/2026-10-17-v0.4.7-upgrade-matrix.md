Reading of the mechanism, confirmed against `@deepseek-ai/dsh-plugin-manager` `reconcile()` in the pinned CLI (`.../dsh-plugin-manager/lib/index.js:322-350`): the bundle list only grows for dependencies that are new relative to the pre-run manifest. The failed first attempt already wrote the dependency, so the second run treats it as pre-existing and never adds it to `dsh.profile.bundles`; the aggregate is installed but never composed.

Classification: this is a property of the pinned official CLI plus pnpm 11 build-script approval over a family that ships native-dependency plugins (`cloudflared`, `ssh2`, `cpu-features`), not a 0.4.6 -> 0.4.7 change; the 0.4.6 install in section 5 hits the same approval prompt. It is a user-visible trap in the documented fresh-install path and belongs in the v0.4.7 release notes alongside the two supported entry points.

## 5. Scenario B - upgrade 0.4.6 -> 0.4.7 through the plugin-manager path

### 5.1 Method, and the one substitution

Baseline (`/tmp/dsh-verify-0_4_7-homeB`, profile `upgradeB`): `dsh --from-default-profile web --profile upgradeB --dump-config`, then `dsh plugin --profile upgradeB add '@linxin666/dsh-web-all@0.4.6'` from the real registry (`Done in 12.7s`, `ADD_EXIT=0`, bundle registered).

Seeded 0.4.6 profile layer, exactly the shape `setRowEnabled` writes (`packages/dsh-plugin-manager/src/host/rows.ts:262-292`, key set `{id, name, disabled}`):

```
# user overrides written by the plugin manager
- id: web-ui-model-capabilities
  name: '@linxin666/dsh-web-all/model-capabilities'
  disabled: true
- id: web-ui-task-board
  name: '@linxin666/dsh-web-all/task-board'
  disabled: true
```

The `name` values are the composed row names, not the ids: the loader skips a mismatched override with `patch: name mismatch for "web-ui-task-board" (expected "@linxin666/dsh-web-all/task-board", got "web-ui-task-board"), skipping`, so an id-as-name fixture silently tests nothing. With the composed names the profile composes at exit 0 with zero stderr lines and both rows disabled.

Upgrade driver: the production route handlers of this repository's plugin manager, imported from source and served over real HTTP by `/tmp/dsh-verify-0_4_7-harness/gateway-server.mjs`:

```js
import { makeGatewayRoutes } from '<repo>/packages/dsh-plugin-manager/src/host/routes.ts'
const facts = resolveProfile(['node','dsh','--profile',profile], process.env)
const gateway = new CliGateway(facts, process.env, { nativeManager: () => undefined })
const routes = makeGatewayRoutes({ facts, gateway, cliAvailable, fetchManifest })
```

Everything below the route handler is the shipping code path: `updateHandler` -> `CliGateway.update` -> `dsh plugin --profile upgradeB add @linxin666/dsh-web-all@0.4.7` (the pinned CLI, pnpm 11.9.0) -> `verifyBoot` (`dsh --profile upgradeB --dump-config`) -> `pruneOrphanOverrides` -> `writePatchAtomic`.

The substitution is the registry manifest source and only that: `fetchManifest` in production calls `https://registry.npmjs.org/<name>/latest` (`routes.ts:107`), which is still 0.4.6, so the harness injects the same handler's documented `fetchManifest` seam and points it at the local registry, where the packed 0.4.7 exists. The profile's own `.npmrc` points `@linxin666` at the same registry, so the install itself resolves the packed 0.4.7 tree, not the registry copy. Without the substitution the route is inert pre-publish (section 5.3).

## 7. Scenario D - what each entry point actually does

### 7.1 plugin-manager check-updates / update

- `check-updates` (`POST /api/plugin-manager/check-updates`): reads the profile's installed versions and compares them with `registry.npmjs.org/<name>/latest`; observed `{"updates":[]}` pre-publish and, with 0.4.7 advertised, `{"current":"0.4.6","latest":"0.4.7","requiresDsh":">=0.2.1-rc.2","compatible":true,"hostVersion":"0.2.1-rc.2"}`. It performs no write.
- `update` (`POST /api/plugin-manager/update`): refuses while the installed version equals `latest` (HTTP 409, observed twice), runs the pinned CLI's `dsh plugin add`, then `dsh --dump-config` as a preflight, verifies the resulting version, and prunes orphan row overrides in the same transaction with a single `cordis.patch.yml.bak-plugin-manager` backup. Verified end to end in scenarios B and C.
- Pre-publish the pair is effectively inert for 0.4.7: 409 "already at 0.4.6" and an empty `check-updates`, because no manifest at `latest` names 0.4.7 yet.
