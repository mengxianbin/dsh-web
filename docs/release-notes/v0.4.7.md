本次发布把家族适配的官方 cohort 推进到 `0.2.1-rc.2`，宿主下限随之上移；新增 `dsh-remote-bridge`，让已配对的手机通过协议 v1 使用宿主会话；为 Windows x64 会话带来固定的私有 bash；任务看板支持推理档位、自动子任务团队与新建卡片默认值；插件管理器在更新时清理失效的逐行覆盖，并把更新改成与官方管理器一致的「先卸载再安装」。技能中心给插件提供的技能加上启用开关，远程网页可以在连接时自选配对网络来源。

> **重要变更（宿主下限提升到 `>=0.2.1-rc.2`）**：家族全部包与插件脚手架声明 `dsh.engines.dsh >=0.2.1-rc.2`（上一版本声明的是 `>=0.2.0-rc.2`），同名 host peer 一并保持一致。官方 CLI 的 npm `latest` 仍是 `0.2.0-rc.2`，`0.2.1-rc.2` 只在 `next` 频道，因此仍在稳定版 CLI 上的用户无法经插件管理器自动更新：更新会被拒绝并返回 412，提示该目标要求 DSH `>=0.2.1-rc.2`（附当前 DSH 版本），需先升级 DSH。恢复步骤：先安装 `0.2.1-rc.2` 的 CLI，再更新家族包。
> **会真正迁移的入口只有一个**：经插件管理器更新（含聚合包旧名的迁移分支）会做预检、版本断言与回滚。本版本**没有** Doctor 启动前迁移——doctor 包当前只是 tombstone，`legacy-migration.ts` 里提到的启动前置消费者在本版本并不存在；直接用 `dsh web` 启动宿主也不执行任何安装或预检，旧 profile 会一直保持原样，直到用户经插件管理器更新。因此请经插件管理器完成更新，需要手工处理时用 `dsh plugin --profile <name> add @linxin666/dsh-web-all@0.4.7`，不要指望启动即升级。
> **第四条路径较弱**：`dsh-update` 家族插件在 profile 内直接跑包管理器更新，没有备份、没有预检、没有回滚，也不会清理失效的行覆盖。能用插件管理器时优先用插件管理器。
> 已退场的插件行不再留下失效的逐行覆盖：更新时插件管理器按组合后的 profile 清理行 id 已不存在的覆盖，先备份 patch 文件，无可清理项时不写入。
> `@linxin666/dsh-client-ui-model-capabilities` 已退场，其 cordis 行 id `web-ui-model-capabilities` 随之消失：既有 profile 若记录过该行，得到的是上一条的清理行为，而不是每次启动一条永久告警。
> 四个卫星仓已先于本 tag 发布 `0.4.7`，聚合包按 semver 消费它们：
> - 皮肤中心（`dsh-skins`）`0.4.7`
> - 宠物（`dsh-pet`）`0.4.7`
> - 社区插件索引（`dsh-community-plugins`）`0.4.7`
> - 预设中心（`dsh-presets`）`0.4.7`
> **已知限制（`0.4.6` 升级到 `0.4.7` 时）**：清理失效行覆盖的代码只在插件管理器的「更新」任务里执行，而把 `0.4.6` 升到 `0.4.7` 的那次更新由宿主中已加载的 `0.4.6` 代码完成，因此它不会清理 `web-ui-model-capabilities` 的旧覆盖。组合结果本身仍然正确，但每次执行 `dsh --dump-config` 或查看 CLI 日志都会看到 `patch: entry "web-ui-model-capabilities" not found` 诊断，也不会生成 `.bak-plugin-manager` 备份。下一次经插件管理器的更新由 `0.4.7` 的代码执行，会顺带自动清理；在那之前可以手工处理：先备份，再编辑 `$DSH_HOME/profiles/<profile>/cordis.patch.yml`，删掉 `id` 为 `web-ui-model-capabilities` 的那一段。启动后自动清理会随下一个版本发布。

This release advances the family's official cohort to `0.2.1-rc.2` and raises the host floor with it, adds `dsh-remote-bridge` so a paired phone can use host sessions over protocol v1, brings a pinned private bash to Windows x64 sessions, gives the task board reasoning effort, automatic subtask teams and new-card defaults, and has the plugin manager prune stale per-row overrides on update while updating through the same remove-then-install path the official manager uses. The skill explorer gains an enable switch for plugin-provided skills, and the remote Web GUI lets you choose the pairing network source when connecting.

> **Important change (the host floor moves to `>=0.2.1-rc.2`)**: every family package and the plugin scaffold now declares `dsh.engines.dsh >=0.2.1-rc.2` (the previous release declared `>=0.2.0-rc.2`), with the matching host peer kept in step. npm `latest` for the official CLI is still `0.2.0-rc.2` and `0.2.1-rc.2` is only on the `next` tag, so a user on the stable CLI cannot auto-update through the plugin manager: the update is refused with 412 and a message that the target requires DSH `>=0.2.1-rc.2` (with the current version), telling them to upgrade DSH first. Recovery: install the `0.2.1-rc.2` CLI first, then update the family.
> **Only one entry point really migrates**: updating through the plugin manager (including the legacy aggregate-name migration branch) preflights, asserts the resulting version and can roll back. This release has **no** Doctor pre-launch migration — the doctor package is only a tombstone today and the launcher consumer `legacy-migration.ts` refers to does not exist here — and starting the host with a direct `dsh web` performs no install and no preflight, so an old profile stays exactly as it is until the user updates through the plugin manager. Update through the plugin manager, or run `dsh plugin --profile <name> add @linxin666/dsh-web-all@0.4.7` by hand; do not expect a start to upgrade anything.
> **The fourth path is weaker**: the `dsh-update` family plugin runs a package-manager update inside the profile with no backup, no preflight, no rollback, and it does not prune the stale row override either. Prefer the plugin-manager path.
> Retiring a plugin row no longer leaves a stale per-row override behind: on update the plugin manager prunes overrides whose row id the composed profile no longer declares, backs the patch file up first, and writes nothing when there is nothing to prune.
> `@linxin666/dsh-client-ui-model-capabilities` is retired and its cordis row id `web-ui-model-capabilities` is gone: a profile that recorded that row gets the pruning behaviour above instead of a permanent warning on every start.
> The four satellites already published `0.4.7` before this tag, and the family consumes them by semver:
> - Skin center (`dsh-skins`) `0.4.7`
> - Pet (`dsh-pet`) `0.4.7`
> - Community plugin index (`dsh-community-plugins`) `0.4.7`
> - Preset center (`dsh-presets`) `0.4.7`
> **Known limitation (upgrading `0.4.6` to `0.4.7`)**: the code that prunes a stale per-row override runs only inside the plugin manager update job, and the update that takes a host from `0.4.6` to `0.4.7` is performed by the `0.4.6` code already loaded in that host, so it cannot prune the `web-ui-model-capabilities` override it retires. The composition itself stays correct, but every `dsh --dump-config` run and every CLI log shows a `patch: entry "web-ui-model-capabilities" not found` diagnostic, and no `.bak-plugin-manager` backup is written. The next update through the plugin manager runs under `0.4.7` code and clears it as part of that run; until then you can do it by hand: back the file up, then edit `$DSH_HOME/profiles/<profile>/cordis.patch.yml` and remove the entry whose `id` is `web-ui-model-capabilities`. Pruning after boot ships in the next version.

### New Features

- [remote-bridge] New `dsh-remote-bridge` package: the host half serves session roster, history and prompting to a paired phone over protocol v1, pairing by a one-shot token plus a P-256 challenge-response

- [remote-bridge] The roster and history baseline ride the protocol, session titles and metadata arrive with them, and a delegated session is addressed through its parent
