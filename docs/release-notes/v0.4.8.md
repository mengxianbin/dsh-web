本次发布把聚合包的家族行改为直挂真实包，兼容层不再随聚合包下发，聚合客户端 bundle 从 2.9 MB 缩到 22 KB；远程桥接成为聚合包的一行，并沿协议 v1 继续扩展分叉、增量名册、帧压缩、后台任务与子代理线程；新增 `dsh-task-board-remote`，把任务看板带上远程面；设置页给出全家桶遥测开关，技能中心支持筛选、折叠与导入，任务看板增加每日令牌上限与执行结算记录，SSH 支持按主机开启代理转发，用量卡标出 DeepSeek 峰谷时段。插件管理器在这一版补齐了三处更新链路的边界：失效行名修复、被替换 bundle 的层序恢复，以及「无法判定」与「DSH 版本过低」的区分。

> **会真正迁移的入口只有一个**：经插件管理器更新（含聚合包旧名的迁移分支）会做预检、版本断言与回滚，它是唯一具备这三件事的路径。本版本仍然**没有** Doctor 启动前迁移——`dsh-doctor` 当前只是 tombstone，`legacy-migration.ts` 里提到的启动前置消费者在本版本并不存在；直接用 `dsh web` 启动宿主不执行任何安装或预检，旧 profile 会一直保持原样。请经插件管理器完成更新，需要手工处理时用 `dsh plugin --profile <name> add @linxin666/dsh-web-all@0.4.8`。`dsh-update` 家族插件是第四条路径：它搬动版本并校验结果，但没有备份、没有预检、没有回滚，也不修行名。
> **行名重写会在启动时自动补齐**：0.4.8 的家族行以真实包名挂载（例如 `@linxin666/dsh-client-ui-task-board`，而不是 `@linxin666/dsh-web-all/task-board`）。仍带旧名的 profile 行在这一次启动里被整行跳过，用户此前保存的 `disabled` 与 `config` 因此不生效——被关掉的插件可能重新挂上。插件管理器在宿主启动稳定 1.5 秒后改写行名，同一处修复也在更新任务里执行；写入前先备份到 `cordis.patch.yml.bak-plugin-manager`，只在确有差异时写，可重复执行。运行中的宿主是否即时重读这份文件没有保证，**重启一次**即可完成修复；磁盘上不会丢数据，也不会多出一行。
> **残留告警**：只有 profile 的 bundle 声明可解析时，插件管理器才会自动清理已退场的 `web-ui-model-capabilities` 覆盖行；CLI 建出的 profile 只在 `dsh.profile.bundles` 里声明 `@deepseek-ai/dsh-base` 与 `@deepseek-ai/dsh-web-app`，并不安装它们，判定因此为「无法判定」，清理逻辑不删任何东西。所以这类 profile 在每一条升级路径上（包括经插件管理器更新）都会留下该覆盖行：组合结果本身仍然正确，唯一症状是每次 `dsh --dump-config` 与 CLI 日志里都会重复一条 `patch: entry "web-ui-model-capabilities" not found`。手工处理：先备份，再编辑 `$DSH_HOME/profiles/<profile>/cordis.patch.yml`，删掉 `id` 为 `web-ui-model-capabilities` 的那一段。
> `@linxin666/dsh-client-ui-model-capabilities` 继续处于退场状态，没有替代包：自定义模型的输入类型与推理档位由官方 Models 设置页编辑。它的 cordis 行不再让组合失败，而是挂载空壳；退场插件名册由 `aggregate.yml` 的 `retiredPlugins:` 生成（本版改为从清单生成，不再手写），命中的说明符在加载前被跳过，并在插件清单里给出一条 “Removed ...” 说明。
> **远程桥接现在是聚合包的一行**（`web-ui-remote-bridge`）：装载聚合包的 profile 升级后即带一个协议 v1 监听器，监听 `/ios/v1`，另有一个只对来自本机的请求开放的配对令牌端点 `/remote-bridge/pair/token`，无需再单独安装。它与独立安装的 `@linxin666/dsh-remote-bridge` 互斥单实例（`mountOnce`），不会双注册路由。
> **故障单元变大了**：家族行直挂真实包之后，某个家族插件导入或启动失败不再被容错外壳隔离成「一行降级」，而是让整个 loader 组回滚。这是有意的取舍（见 issue #1901 的决定记录），原先由宿主掌握的启动审计行为不变。
> **pnpm 供应链限制**：pnpm 配置若启用 `minimumReleaseAge`（常见默认 24 小时），在包发布后不久执行的更新会被挡住。补救办法是在 profile 的 `pnpm-workspace.yaml` 里为 `@linxin666/*` 补上 `minimumReleaseAgeExclude`。
> **卫星范围在同一批次里对齐**：四个卫星仓先各自发布 `0.4.8`，registry 可解析之后，聚合包的依赖范围才从 `^0.4.7` 抬到 `^0.4.8`：
> - 皮肤中心（`dsh-skins`）：`@linxin666/dsh-client-ui-skin-center@0.4.8`
> - 宠物（`dsh-pet`）：`@linxin666/dsh-pet@0.4.8`
> - 社区插件索引（`dsh-community-plugins`）：`@linxin666/dsh-client-ui-community-plugins@0.4.8`
> - 预设中心（`dsh-presets`）：`@linxin666/dsh-client-ui-preset-center@0.4.8`

This release mounts the aggregate's family rows on their real packages so the compat layer no longer ships with the aggregate and its client bundle drops from 2.9 MB to 22 KB, makes the remote bridge a row of the aggregate and keeps extending protocol v1 with forking, incremental roster and board answers, frame compression, background jobs and subagent threads, adds `dsh-task-board-remote` to put the task board on the remote surface, ships a family-wide telemetry switch, gives the skill center filtering, folding and importing, adds a daily token cap and a settled-execution record to the task board, brings opt-in per-host SSH agent forwarding, and marks the DeepSeek peak and off-peak clock on the usage card. The plugin manager closes three boundaries of the update path in this version: the stale row-name repair, the layer order of a replaced bundle, and telling "cannot verify" apart from "DSH too low".

> **Only one entry point really migrates**: updating through the plugin manager (including the legacy aggregate-name migration branch) preflights, asserts the resulting version and can roll back, and it is the only path with all three. This release still has **no** Doctor pre-launch migration — the doctor package is only a tombstone today and the launcher consumer `legacy-migration.ts` refers to does not exist here — and starting the host with a direct `dsh web` performs no install and no preflight, so an old profile stays exactly as it is. Update through the plugin manager, or run `dsh plugin --profile <name> add @linxin666/dsh-web-all@0.4.8` by hand. The `dsh-update` family plugin is the fourth path: it moves versions and verifies the result, but it has no backup, no preflight, no rollback and it does not repair row names.
> **The row-name rewrite happens on its own at startup**: the 0.4.8 family rows mount under their real package names (for example `@linxin666/dsh-client-ui-task-board` instead of `@linxin666/dsh-web-all/task-board`). A profile row still carrying the old name is skipped whole for that boot, so the `disabled` and `config` the user saved stop applying — a plugin they had switched off can mount again. The plugin manager rewrites the name 1.5 s after the boot settles, and the same repair runs inside the update job; it backs the file up to `cordis.patch.yml.bak-plugin-manager` first, writes only on a real difference, and repeats safely. Whether a running host re-reads the file is not guaranteed, so **restart once** to complete the repair; nothing on disk is lost and no second row appears.
> **Residual warning**: the plugin manager prunes the retired `web-ui-model-capabilities` override automatically only when the profile's bundle declarations resolve; a CLI-created profile lists `@deepseek-ai/dsh-base` and `@deepseek-ai/dsh-web-app` in `dsh.profile.bundles` without installing them, so the check answers unknown and the prune deletes nothing. Such a profile therefore keeps that override row on every upgrade route, a plugin-manager update included: the composition itself stays correct, and the only symptom is the repeated `patch: entry "web-ui-model-capabilities" not found` line on each `dsh --dump-config` and in CLI logs. To do it by hand: back the file up, then edit `$DSH_HOME/profiles/<profile>/cordis.patch.yml` and remove the entry whose `id` is `web-ui-model-capabilities`.
> `@linxin666/dsh-client-ui-model-capabilities` stays retired with no replacement package: a custom model's input types and reasoning levels are edited on the official Models settings page. Its cordis row no longer fails the composition, it mounts nothing; the retired-plugin roster is generated from `aggregate.yml`'s `retiredPlugins:` section (generated in this version instead of hand-written), the matching specifiers are skipped before loading, and the inventory shows a "Removed ..." line for each.
> **The remote bridge is now a row of the aggregate** (`web-ui-remote-bridge`): a profile that finds the aggregate already carries a protocol v1 listener after the upgrade, listening on `/ios/v1`, plus a pairing-token endpoint on `/remote-bridge/pair/token` admitted only from this machine, with no separate install needed. It is single-instance against a standalone `@linxin666/dsh-remote-bridge` (`mountOnce`), so the routes are never registered twice.
> **The fault unit got bigger**: now that family rows mount their real packages, a family plugin that fails to import or start is no longer contained as one degraded row by the fault-isolation shell; it rolls the whole loader group back. That is a deliberate trade (see the decision record for issue #1901), and the boot-audit behaviour the host owns is unchanged.
> **pnpm supply-chain limit**: a pnpm configuration that enables `minimumReleaseAge` (24 hours by common default) holds an update that runs soon after publication. The remedy is `minimumReleaseAgeExclude` for `@linxin666/*` in the profile's `pnpm-workspace.yaml`.
> **The satellite ranges move in the same batch**: the four satellite repositories publish `0.4.8` first, and only once the registry resolves them does the aggregate's dependency range move from `^0.4.7` to `^0.4.8`:
> - Skin center (`dsh-skins`): `@linxin666/dsh-client-ui-skin-center@0.4.8`
> - Pet (`dsh-pet`): `@linxin666/dsh-pet@0.4.8`
> - Community plugin index (`dsh-community-plugins`): `@linxin666/dsh-client-ui-community-plugins@0.4.8`
> - Preset center (`dsh-presets`): `@linxin666/dsh-client-ui-preset-center@0.4.8`
