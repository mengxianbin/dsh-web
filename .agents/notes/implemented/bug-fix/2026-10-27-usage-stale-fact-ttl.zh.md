# Agent Note: 探测陈旧事实 TTL

Status: implemented

## 问题

`UsageService.probeRoute` 在探测失败时保留上一次的余额/套餐事实（"stale but useful"），且无任何上限。当 MiMo 平台 SSO cookie 过期后，余额探测每轮都返回 HTTP 401，而快照持续服务最后一次成功的结果——侧栏 glance 连续 27 小时展示冻结的 `¥36.87`，线上文档里没有任何陈旧信号。错误行记录了失败，但事实本身永不过期，失效通道把冻结数值无限期地当现值展示。「无凭据」路径本就会重置行（保留的事实永远不会刷新），但「有凭据、探测一直失败」没有对应的降级。

## 决策

在 `src/host/usage-service.ts` 中加入 `STALE_FACT_TTL_MS`（2 小时）与 `pastFactTTL()` 辅助函数。探测失败时，仅当该事实自身的 `updatedAt`（最后一次成功探测时刻）在 TTL 内才保留；超过后事实降级为无，错误行保留以解释缺失。TTL 从事实自身的探测时刻起算，因此经持久化快照跨重启存活，从旧磁盘状态携带的事实会在首个失败周期老化出局。缺少数字型 `updatedAt` 的事实（旧持久化形态）视为已过 TTL——降级而非永久携带。两个探测半区（余额与套餐）共用该规则。

## 备选方案

- 连续失败计数器：否决——除非单独持久化，否则跨重启归零，且计数到时间的映射随轮询间隔变化。事实自身年龄已持久化且与间隔无关。
- 首次失败即丢弃事实：否决——瞬时抖动（provider 重启、网络闪断）会让数值频繁空白，这正是保留机制要避免的。
- 只在 UI 标陈旧、host 不设过期：否决——glance 仍需一个可信的年龄边界来决定何时隐藏而非标记，且每个其他消费方（宠物公告、设置分区）都要重新实现一遍。

## 后果

TTL 内行为不变（陈旧行数值 + 错误行）。超过 TTL 后 glance 数值降级为破折号，宠物气泡回落为台账用量气泡；探测成功立即恢复事实。配套的 UI 改动（deepseek-harness `UsageGlance`，FORK usage-glance-stale-fact-ttl）在「仍新鲜的携带窗口」内把保留数值标陈旧——星号、置灰、tooltip 显示事实自身的探测时刻——两半合起来覆盖失效全程：新鲜携带期有标记，老化后消失。

## 测试

`tests/usage-service.spec.ts` 在「probes and per-fact errors」下新增两例：余额事实在 TTL 内的失败探测下存活、超过 TTL 后降级为无（错误行保留）；套餐事实遵守同一 TTL。测试套件共享的 `afterEach` 现在调用 `vi.useRealTimers()`，防止假时钟泄漏进生命周期与持久化测试。
