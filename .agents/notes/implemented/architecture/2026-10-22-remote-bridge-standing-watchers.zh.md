# Agent Note: 桥自持跟随流，卡与通知才不需要客户端在

Status: implemented

相邻面：[推送通道](2026-10-21-remote-bridge-push-notifications.md) 拥有 §28，[一张卡排下几个会话](../feature/2026-10-22-remote-bridge-live-activity-rows.md) 拥有 §29。本记录拥有的是：没有任何客户端连着时，那条让两者都能发出的 `session/follow` 流由谁持有。

## Problem

§28 与 §29 都在 `turn/end` 上投递，而桥见到过的每一个 `turn/end` 都来自客户端自己打开的 `session/follow`。锁屏的手机就是被 iOS 关掉 socket 的手机，于是通知与卡唯一存在的理由——那个没人看着的时候结束的回合——恰好是桥什么都没产出的时刻：没有流、没有事件、没有推送。一张必须在锁屏上说 `ended` 的卡，和一条要到下次解锁才送达的通知，是同一个失败的两个面。

## Decision

- **流由宿主侧一个组件自己持有。** `StandingWatchers`（`packages/dsh-remote-bridge/src/host/watchers.ts`）负责它们，且只在存在推送路径时可用：活卡通道与 APNs 通道都没配置时 `enabled` 为假，不开流也不记日志，于是投递不出去的桥连会话都不去读。
- **触发者是设备名册，单位是有卡的那个会话。** 某会话只要在 `$DSH_HOME/remote-bridge/devices.json` 里持有至少一个活卡令牌，桥就为它开一条 `session/follow`，用的是客户端调用同一个进程内 owner peer，所以向 harness 要的正是手机本来会要的东西；`maxMessages` 默认取客户端快照用的同一个 `SNAPSHOT_MAX_MESSAGES` 窗口。
- **增删都按名册对账，不看某条连接的生死。** `BridgeConnection` 只多了一个钩子 `onPushRegistered`：`push.register` 存下令牌之后调用它，并在调用处做保护，常驻观察者永远不能把注册变成失败；回收死令牌的 `410` 调同一个 `sync()`，挂载时那次名册读取则对账文件里已有的令牌。某会话的最后一个活卡令牌消失，它的流就关（`watcher close session=… reason=cards-gone`）。
- **数量有上限，拒绝按会话只记一行。** `WATCHER_LIMIT` 为 64；超过之后该会话不开流，且只有一行说明（`watcher refused session=… reason=limit(64)`），并记住这条会话，后续注册不再重复刷。
- **自己结束的流一秒后重新武装一次。** `WATCHER_REOPEN_MS` 为 1000 毫秒：跟随流被关不等于会话有结论，仍有卡的会话继续被看着。
- **失败只记一行，从不抛给调用方。** 宿主拒绝的流、中途抛错的 follow、读不到名册的对账，各自记一行 `watcher` 日志后丢弃；被拒绝的流不重试，直到名册再变。
- **一个 `turn/end` 同时供给两个面，并且经由安静门。** 观察者把回合结束登记进 `TurnEndQuietGate`，并记一行 `watcher turn-end session=… reason=… held=quiet-gate`；宿主报告该会话安静时由门发出，通知在前、结卡在侧（这条规则的家在[`§28` 的安静门](2026-10-21-remote-bridge-push-notifications.md)）。没装门的观察者集合（例如套件自己拼的）仍然在帧上上报，记 `pushed=card` 或 `pushed=notification-only`。
- **不加第三层去重。** 桥在看的会话被客户端同时打开时，同一个 `turn/end` 会上报两次；§28.5 的 `sessionId+event` 窗口与 §29 的内容键已经把这件事定下来，测试断言的是一张卡、一条通知、一行日志。

## Testing

`tests/watchers.spec.ts`（11 例）在连接层覆盖：有卡的会话各一条流以及它请求的地址、被看的回合结束时卡被结掉且 §28 通知同时在侧、没有推送路径的桥什么都不开且不记日志、会话失去最后一张卡时流关闭、数量到上限且拒绝只记一次、自己结束的流能接住下一个回合、宿主拒绝的流在不碰任何帧的情况下存活、两个流报同一个 `turn/end` 仍只产出一张卡与一条通知、桥被 dispose 时所有流关闭、`push.register` 就是武装观察者的那一步，以及被扣住的回合结束能在子会话落定通知之后存活。`pnpm typecheck` 为绿，包内 45 个文件 626 个用例为绿。

## Alternatives considered

- **让客户端跨锁屏把流留着。** 否决：socket 活多久是 iOS 决定的，桥无从争辩，而最要紧的那个面——锁屏——恰恰是 App 不在的状态。
- **用定时器对账名册。** 否决：设备名册的变化本来自己会说话（`push.register` 写入令牌、`410` 回收令牌），轮询会是对名册已经持有的同一事实的第二种读法。
- **记住每条流的位置并续接。** 否决：观察者服从的是令牌的寿命而不是流的寿命；按名册重开让所有状态都留在手机写的那份文件里，而记住的游标会变成第二份要失效的状态。
- **给观察者自己的上报再加一层去重。** 否决：§28.5 与 §29 已经把重复上报定下来，第三把键是对同一事件的第二个意见，还自带一套 bug 面。
- **观察者开不起来时让 `push.register` 失败。** 否决：注册的全部职责就是那个令牌，观察者是后台工作，所以钩子只在调用处做保护，而不给它拒绝手机的权力。

## Consequences

- 没配推送通道的桥什么都不开，于是在投递不了的地方这项能力也不花成本。
- 桥自己最多持有 64 条跟随流及其窗口，这个上限存在的理由就是那份内存。
- 被拒绝的流在那份名册状态下一直是被拒绝的——只有名册再变才会重新武装，这也是拒绝只记日志而不重试的原因。
- 桥与客户端可以同时看同一个会话；让那次双重观察在卡上与锁屏上仍是一件事的，是既有的两层去重。
