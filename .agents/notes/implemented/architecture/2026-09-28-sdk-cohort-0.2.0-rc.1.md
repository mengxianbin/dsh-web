# Agent Note: SDK cohort 0.2.0-rc.1

Status: implemented

## Problem

The integration line declared `0.1.7-rc.2` while the official family published `0.2.0-rc.1` on 2026-09-28 (npm `next`, host CLI at 12:34Z), and the publish is not a version bump on the same line: it opens the `0.2.0` series and ships the changes the release notes group under 体验优化, 问题修复 and 其他变更. Staying put would leave the family's machine-readable floor naming a host the line has already left, and would leave the family on the rc line while the official shell moves to the 0.2 composition.

Two facts shaped this move. First, the active host is far ahead of the declared floor: the running DeepSeek Harness desktop client, the Homebrew `dsh` CLI and every local profile all sit on `0.1.7-rc.2`, so the plugin SDK and the runtime that hosts it stay on the same release line across this change. Second, a rendered answer patch is not a hook input: the 0.2 shell streams answer text through character-data mutations that the aggregate's body-mutation hub was paying a full-frame rescan for on every token, without any of its hooks reading the changed subtree.

## Decision

The whole cohort moves to `0.2.0-rc.1` in one change, in the isolated worktree `feat/dsh-0.2.0-rc.1-upgrade` (`/Users/zcl/code/.worktrees/dsh-web/feat-dsh-0.2.0-rc.1-upgrade`) created by `wt switch --create` from the local `dev` tip (`331b1118`, one unpushed commit ahead of `origin/dev`), so the shared checkout and the running GUI are untouched until integration. It follows [sdk-cohort-0.1.7-rc.2](2026-09-24-sdk-cohort-0.1.7-rc.2.md), which keeps owning the rc.2 move; this note owns the 0.2.0-rc.1 move and supersedes none of it.

### An adopted experience improvement that was reverted

The 0.2 shell streams answer text, and React commits it as character-data mutation records. The aggregate's page-wide body-mutation hub fed those records to the shim and to every DOM-mounting family plugin, each of which then rescanned the frame — per token, for a subtree none of them reads.

A page-wide batch filter was implemented in `shared/client/body-mutations.ts` (a cross-bundle `Symbol.for` slot, replaced rather than composed, failing open on any unknown record) plus an `isUnobservableAnswerPatch` predicate in the aggregate shim, with tests at both levels. It was then reverted before this change was committed, because its correctness rested on an assumption the shell does not guarantee: the predicate recognised answer content by a container attribute and by the record's `target` being an ancestor of the added nodes, which holds for the common streaming path but not for a React commit that re-creates the answer container's parent — an unobservable-under-test case, and a misclassified batch does not merely waste a frame, it leaves stamped hooks stale. The measured win was bounded (one frame scan per streaming commit, with the per-frame scheduling already shared across all subscribers), so an unproven predicate was not worth the failure mode. The full reasoning and the rejected shapes stay in this note: the hub keeps no filter, and a future attempt should first prove the record-shape assumption against a real streaming session rather than against fixtures.

## Alternatives considered

**Move only the host and keep the SDK packages on rc.2.** Rejected: the family's floor, peers, badge and mount pins are one contract, and splitting them across two release lines is exactly the state [dsh-host-floor-tracks-cohort](2026-09-01-dsh-host-floor-tracks-cohort.md) exists to prevent.

**Leave the family on the rc line until `0.2.0` is stable.** Rejected by the operator's request: the 0.2.0 candidate carries the improvements this change exists to adopt, and the line the family adapts to is the one the released host serves.

**Keep the body-mutation filter.** Rejected on evidence: the predicate's correctness depended on a DOM-shape assumption that only a real streaming session can confirm, and its failure mode silently degrades every DOM hook on the page. A bounded frame-scan saving does not justify an unproven predicate.

**Adopt the official schedule bundle as the task-board's timing engine.** Rejected for this cohort: the bundle ships disabled by default, so adopting it would either ship a disabled feature or flip a product decision that the official release deliberately left to users. The task ledger's own scheduler stays authoritative; the migration is open work, not a cohort obligation.

**Add `@deepseek-ai/dsh-client-product-analytics` as a root dependency to satisfy the new type-only reference.** Rejected: the reference lives in a package-private module-graph file that no `exports` subpath serves, and 34 identical rows at rc.2 already name packages this repository never installs. Adding a dependency would institutionalise an upstream packaging artifact as a requirement.

## Consequences

- The declared floor, the host peer, the badges, the CI/release mount pins and the desktop-free host-floor set all name `0.2.0-rc.1`, and the lockfile resolves every `@deepseek-ai/dsh-*` key at exactly that version.
- The running desktop client and the local `desktop` profile still carry `0.1.7-rc.2` shadow copies. They converge when the host CLI moves and the profile is refreshed; until then the profile tree keeps working on its own cohort, and no profile surgery is attempted against a live instance.
- The satellites (`@linxin666/dsh-pet`, `dsh-client-ui-skin-center`, `dsh-client-ui-community-plugins`, `dsh-client-ui-preset-center`) declare `>=0.1.7-rc.1` as their own floor. They accept the new host (a `>=` floor is satisfied by a higher host), and they move to the aligned version in their own repositories.
- No `desktop/` tree exists on this base, so the sixth host-floor surface named by [dsh-host-floor-tracks-cohort](2026-09-01-dsh-host-floor-tracks-cohort.md) — the packaged desktop runtime pin — has nothing to move. There is no desktop re-release pending from this change.
