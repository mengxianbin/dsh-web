# Agent Note: SDK cohort 0.2.0-rc.2

Status: implemented

## Problem

集成分支声明的是 `0.2.0-rc.1`，而官方家族已在 2026-09-29 发布 `0.2.0-rc.2`（npm `next`，tarball 时间戳 09:40Z），并且真正承载本仓插件的运行时早已越过声明下限：正在运行的 DeepSeek Harness 桌面客户端内置 `@deepseek-ai/dsh-desktop-runtime@0.2.0-rc.2`，其中携带 `@deepseek-ai/dsh@0.2.0-rc.2` 及该 cohort 的其余包。按兵不动会让家族的可读下限指向一个运行中客户端已经离开的宿主，等于让安装者去装一个受支持的客户端已不再提供的版本。

两个事实塑造了本次迁移。其一，这是同一线上的候选版本推进，而非新系列：本仓消费的全部 68 个 `@deepseek-ai/*` 包都在 `next` dist-tag 下发布了 `0.2.0-rc.2`，其中 67 个与 rc.1 的差异仅为自身 peer 与依赖区间里的 cohort 字面量。其二，本仓没有 `desktop/` 目录，因此 [dsh-host-floor-tracks-cohort](2026-09-01-dsh-host-floor-tracks-cohort.md) 点名的打包桌面运行时 pin 在这里依然无从移动。

## Decision

整个 cohort 一次性迁到 `0.2.0-rc.2`，在隔离工作树 `feat/dsh-0.2.0-rc.2-upgrade`（`/Users/zcl/code/.worktrees/dsh-web/feat-dsh-0.2.0-rc.2-upgrade`）中进行，该工作树由 `wt switch --create` 从 `origin/dev`（`65d1f6f4`，与本地 `dev` 顶端一致）创建，因此在整合之前共享 checkout 与运行中的 GUI 不受影响。它承接 [sdk-cohort-0.2.0-rc.1](2026-09-28-sdk-cohort-0.2.0-rc.1.md)：其记录继续拥有 rc.1 迁移与其中记录的 body-mutation 分析；本记录拥有 rc.2 迁移，不取代前者。

### 一个 cohort，一个字面量

48 个文件中共 358 处，另有 `pnpm-lock.yaml`：十六个家族清单、插件脚手架、shared 工作区包、`dsh.engines.dsh` 下限及其逐字相同的 `@deepseek-ai/dsh` 宿主 peer、根清单自身的 SDK devDependencies、发布冷却排除账本（68 条）与两个按新 cohort 重新键入的 `packageExtensions`、根 README 双语徽章（shields 形式 `0.2.0--rc.2`）、CI 与发布挂载冒烟 pin、`shared/web-platform.ts`、`shared/tests/web-platform.spec.ts`、`tests/e2e/mount.e2e.ts`、`scripts/rollout-verify.test.mjs`、`scripts/aggregate.test.mjs`、`packages/dsh-plugin-manager/tests/gateway-jobs.spec.ts` 与 `packages/dsh-liangshen/tests/benchmark-live-run.test.ts` 中的 cohort 字面量，以及 `docs/publish-prep.md`、`docs/plugins.md`、`packages/dsh-web-all/aggregate.yml`、`packages/dsh-i18n/AGENTS.md`、`packages/dsh-remote-web-ui/AGENTS.md` 与六个包 README 配对（其配对记录已重新登记）中的 cohort 表述。指向更早 cohort 的历史叙事——rc.1 记录及其 sidecar、`docs/release-notes/v0.4.4.md`、v0.4.4 归档快照，以及在 rc.1 宿主上执行的两次验证记录——不被改写。

`@deepseek-ai/cordis`（4.0.4）与 `@deepseek-ai/schemastery`（3.18.4）不移动：二者都没有发布 `0.2.0-rc.2`，它们的线是独立的，且 cohort 自身的 peer 仍在指定这两个版本。

### 已发布产物层面的差异

本次迁移依据 registry 核实，而不是依据发布说明推断。68 个被消费的包全部以 `next` 提供 `0.2.0-rc.2`；逐一比对其与 rc.1 孪生版本的清单后可见：67 个是纯粹的 cohort 字面量移动，恰好一个存在结构性变化——`@deepseek-ai/dsh-user-questions`，为新的定时等待模式新增了 `dsh-session`、`dsh-session-projection`、`dsh-typert-protocol` 三个 peer，以及 `schemastery ~3.18.4` 与 `zod ^4.4.3` 两个依赖。该包不在本仓的依赖集合中，因此没有任何解析来自它。

源码导入的全部 86 个 `@deepseek-ai/*` 包（其中 79 个在两个 cohort 上都存在）的两套 tarball 都被解包比对。结果：零个被移除的导出名、任何位置零个被移除的文件、77 个逐字节相同的公开导出面，以及恰好两个纯增量的包——`@deepseek-ai/dsh-client-ui-primitives`（`MenuGroup`、`observeStickyMenuGroups` 及其 CSS module 与类型文件）与 `@deepseek-ai/dsh-user-questions`（定时问答的 projection、工具与 remote-typert 面）。前端 shell 冻结的 `staticModules` 表在两个 cohort 上逐字节相同（`react`、`react/jsx-runtime`、`react-dom`、`react-dom/client`、`@deepseek-ai/cordis`、`@deepseek-ai/dsh-client-store`、`@deepseek-ai/dsh-client-ui-slots`、`@deepseek-ai/dsh-client-ui-primitives`、`@deepseek-ai/dsh-client-ui-dockkit`），因此 `shared/web-platform.ts` 保留其清单，只移动来源注释。官方 Plugins 页的贡献槽位清单与官方对话包的 slot id 集合在两个 cohort 之间各自保持不变，因此没有任何家族注册失去席位。家族两侧（client 与 host）注入的全部 22 个 cordis 服务在 rc.2 语料中依然有声明。没有修补任何已安装文件。

`packageExtensions` 块是针对 rc.2 tarball 重新核实的，而不是照惯例沿袭：`@deepseek-ai/dsh-client-ui-primitives@0.2.0-rc.2` 依然完全不声明 `dependencies`，其产出的 `lib/index.js` 却导入 `anser`、`clsx`、`diff`、`katex`、`mdast-util-*`/`micromark-*` 家族、`shiki`、`simple-icons` 与三个 `@deepseek-ai/dsh-util-*` 面；`@deepseek-ai/dsh-client-store@0.2.0-rc.2` 也依然不声明 `dependencies` 却导入 `immer` 与 `zustand`。两个补丁仍然必需，版本取 cohort 自身的 pin。

## Alternatives considered

**停在 `0.2.0-rc.1`，等 `0.2.0` 稳定。** 否决：运行中的桌面客户端已在提供 rc.2，家族下限将指向受支持客户端已经离开的宿主，而这正是 [dsh-host-floor-tracks-cohort](2026-09-01-dsh-host-floor-tracks-cohort.md) 要防止的漂移；且操作者明确要求适配 rc.2。

**只移动 SDK devDependency 区间，下限、徽章与挂载 pin 留在 rc.1。** 否决：下限、host peer、徽章与挂载 pin 是同一份契约；把它们在两个候选版本之间拆开，正是那份记录禁止的状态。

**为了让 cohort 新增的导出显得「被采纳」，在某个地方使用新的 `MenuGroup` 原语。** 否决：没有任何家族表面渲染吸顶分组菜单，为导出清单而引入 UI 表面本末倒置。深度适配意味着消除重复，而不是为增量导出制造消费者。

**因为官方页面现在提示升级，就删除家族的「检查更新」块。** 依据证据否决：官方改动新增的是提示文案，而 registry 比对与一键更新仍由家族拥有；为一次文案变更删除我们的实现会造成能力回退。

**在本次变更中刷新本地 profile。** 否决：影子拷贝检查未报告任何跨 cohort 错位，profile 由各自的 lockfile 物化，且治理该流程的技能禁止对运行中的 profile 实例执行安装。profile 树保持原样。

## Consequences

- 声明下限、host peer、徽章、CI/发布挂载 pin 与发布冷却账本全部指向 `0.2.0-rc.2`，lockfile 把全部 51 个 `@deepseek-ai/dsh-*` 键解析为恰好该版本，不残留任何 rc.1 条目。lockfile 差异是对称的（815 增、815 删），不含 cohort 之外的任何包移动。
- 正在运行的 DeepSeek Harness 桌面客户端已在提供 0.2.0-rc.2，因此家族与加载它的客户端自 rc.1 迁移以来首次处于同一条线；`pnpm install --frozen-lockfile --ignore-scripts` 在 rc.2 排除账本下通过供应链策略检查。
- 本机 Homebrew 的 `dsh` CLI 仍是 npm `latest` 的 `0.1.7-rc.2`，低于新下限。移动全局 CLI 属于 `dsh-upgrade` 的职责，不属于 SDK cohort 迁移；在它完成之前，由该 CLI 驱动的 profile 低于家族声明下限。这被记录为待办的 rollout 工作。本仓没有可移动的打包桌面 pin，因此本次变更不产生待办的桌面重发。
- 本地 `desktop` profile 保留 `@deepseek-ai/cosmokit` 与 `@deepseek-ai/schemastery` 的实体拷贝，版本与宿主自身相同——即 cohort 检查报告为警告的同一类模块身份隐患，本次迁移未改变它，在版本一致期间无害。
- `@deepseek-ai/dsh-user-questions` 现在为定时等待模式需要 `schemastery` 与 `zod`。本仓没有任何解析该包的地方，因此未新增依赖。
- 本 cohort 的 npm 发布起初并不完整：`@deepseek-ai/dsh-web-app@0.2.0-rc.2` 声明了对 `@deepseek-ai/dsh-client-ui-settings-account@0.2.0-rc.2` 的硬依赖，而该版本在前约 20 分钟内并不存在，因此 `npm install -g @deepseek-ai/dsh@0.2.0-rc.2` 以 `ETARGET` 失败——而这正是 CI 与发布挂载冒烟 lane 所执行的步骤。上游在整合之前发布了它：从 `@deepseek-ai/dsh@0.2.0-rc.2` 出发的闭包遍历现在解析出 252 个 cohort 包且无一缺失，同一条安装命令可以完成，挂载冒烟也在该 registry 形式下通过。
- 没有发布任何包，没有改动任何 `@linxin666/*` 包的版本，也没有读入或修改任何 DSH 源码 checkout。

## Testing

在隔离工作树中对已提交的树运行：`pnpm install --frozen-lockfile --ignore-scripts`（CI 的供应链形式，证明已提交的 lockfile 可解析并通过发布冷却策略）以及完整 lane 序列 `pnpm typecheck`、`pnpm sync-shared:check`、`pnpm libs:check`、`pnpm build`、`pnpm test`、`pnpm test:scripts`、`pnpm runtime-deps:check`、`pnpm aggregate:check`、`pnpm emoji:check`、`pnpm test:standards`、`pnpm docs:check`、`pnpm i18n:check`，最后再跑一次 `pnpm libs:check` 证明构建没有改动已提交的 `lib/` 指纹。

本次 cohort 迁移无需源码修复：类型检查在零源码改动的前提下针对 rc.2 devDependencies 通过，这与「仅有增量」的产物差异一致。`bash scripts/e2e-mount.sh` 以 CI 形式针对从 registry 安装的 scratch `@deepseek-ai/dsh@0.2.0-rc.2` 宿主通过，家族 tarball 由本 checkout 打包：聚合包经 `dsh plugin --profile web add` 挂载、`dsh web` 在 OS 分配端口上以带 token 的 URL 启动、Playwright 无头 lane 通过，无内置右侧面板、无崩溃标记。该次运行使用的是 lane 的 registry 形式：钉定的 `npm install -g @deepseek-ai/dsh@0.2.0-rc.2` 宿主。同一条冒烟最初曾在以 `overrides` 补齐当时未发布的 `@deepseek-ai/dsh-client-ui-settings-account@0.2.0-rc.2` 的宿主上跑过一次（见 Consequences），待上游发布后又以 registry 形式复跑。
