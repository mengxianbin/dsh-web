# Agent Note: 为认领中的用户提问保留一段宽限期

Status: implemented

## Problem

最后一个配对客户端一离开，桥就把全部用户提问当即释放：`BridgeHub.detach` 放弃所有 approval 并调用 `QuestionClaims.withdrawAll()`，每个未结算的认领都被交给宿主自己的应答链。于是 Mac 上出现了手机再也画不出的那张卡。

iOS 在应用进入后台后不久就挂起它，socket 随之断开；而推送通知只携带一个事实：`whale://session/<id>`。手机只有在桥仍持有认领时才画得出提问卡片，也只有重连之后才读得回它。因此在最后一次离开时就释放，等于在手机恰好无法作答的那一瞬间替它决定了这个问题。2026-10-23 10:18 实测：点开通知落在一个没有任何卡片的会话上，宿主也什么都没持有——认领在约二十秒前、挂起的应用 socket 断开时就已释放。

同一条路径上还有第二个缺陷。`BridgeHub.replayQuestions` 对每个认领都发出 `questionPayload('open', claim)`，于是一个 `continued` 认领——宿主前台等待已经结束、答案要经宿主 Remote `answer` 送回去的那种——被当作 `open` 重新交给手机，让它去等一个早已继续走下去的 agent。

## Decision

- `user-questions/request` 上的认领现在比最后一个配对客户端多活 `QUESTION_CLAIM_GRACE_MS`（60 000 毫秒），从该客户端离开的时刻起算。`BridgeHub.detach` 照旧立刻放弃 approvals，对用户提问则改为布下这段宽限期，而不是直接撤回。
- 每座桥只有一段宽限期，因为认领表是全局的：一个 `setTimeout`；若离开事件在它已经运行时再到达，就保持不动，所以第二次离开不会延长它。
- `BridgeHub.attach` 在接入的连接已配对时取消它——回来的这台手机正是宽限期为之保留的对象。`dispose()` 清除它并立即释放：卸载中的桥不是一台离开的手机。
- 定时器带 `unref`，与单个认领布下的 deadline 定时器一致，因此被持有的提问永远不会让宿主进程活着。
- 到期时执行的一直是那次释放的同一段代码：`approvals.abandonAll()`、`questions.withdrawAll()`，以及同样的 `... approval question(s) withdrew: no paired device is connected` 与 `... user question(s) released: no paired device is connected` 日志行。
- `replayQuestions` 现在发出认领自己的状态。它读的是 `QuestionClaims.listed()`——`question.list` 作答所用的那层投影——因此重放出去的卡片与列表里读回来的行是同一个形状，并按其真实状态携带 `open` 或 `continued`。它原先读的 `openClaims()` 已无其他生产调用者，随这次改动删除，而不是留在它重复的那层投影旁边。
- 不改线协议：不新增方法、能力、主题或字段，`hello.r.minor` 不动。

## 认领、agent 的等待与 Mac 侧的卡片

桥持有认领期间，宿主自己的应答链不会被启动，因此 Mac 面板上不会出现这个问题。这一点本决策没有改变，而宽限期挪动的正是它：最后一部手机离开后的最多六十秒内，问题仍然只属于手机，不属于别人。在宽限期内回来的手机会通过重放拿到认领并作答，Mac 此后也不会再看到它。不回来的手机，宽限期结束时问题交给应答链，与改动前 socket 断开那一刻的做法完全一致。

代价落在没有手机回来的情况下：对阻塞式提问，工具在宿主自己的界面能够显示问题之前，还要多等这段宽限期。宽限期是桥原本无法服务的那种情形的一次重连预算，其上界是 `QUESTION_CLAIM_GRACE_MS`，而不是提问自身的寿命。

在宽限期内以未配对状态接入、随后完成配对的 socket 不会取消它：取消的依据是「接入时已经配对」的连接，而重放需要一次已配对的声明。这类设备在声明之后可以通过 `question.list` 读到仍被持有的认领，或者发现宽限期已经先结束。

## Alternatives considered

- **每个认领一个定时器。** 认领表是一张全局映射，所有认领同命运，一个定时器就把这件事说清楚；N 个定时器需要一个清扫器才不会彼此发散，而且仍然要回答「一次释放还是多次释放」。
- **把认领留到提问自身的 deadline。** 阻塞式提问根本没有 deadline——宿主不发明，桥也不允许发明——于是无人作答的认领会被永远持有，而这正是「手机不作答等于拒绝」规则的反面。
- **留到有客户端再次声明为止。** 那是没有上界的释放条件：一台再也不回来的手机（或被卸载的手机）会让宿主的 ask 无限期挂住，Mac 也永远拿不到这个问题。
- **延长认领的 deadline，而不是新增一段宽限期。** 重发提问绝不允许拉长 agent 等待它的时长——这是 approval 重放已经确立的规则。这里要挪动的是认领自己的寿命，不是宿主的 deadline，挪动 deadline 会改变宿主正在等待的东西。
- **任何接入都取消宽限期，无论是否配对。** 未配对的 socket 就是没有 token 的运维浏览器标签页：它画不出卡片也答不了，让它维持一条认领，等于为永远用不上的界面持有问题。
- **用 `openClaims()` 加 `stateOf()` 重放。** 为一个帧读两次同一张表，正是 `questionPayload` 存在的原因所要避免的漂移（「手机被交付的卡片与它从列表读回的卡片不会分叉」）。列表投影本来就同时携带状态与 payload。
- **更短的宽限期（20 秒）。** 它贴合实测的挂起间隔，却不贴合人从看到通知到点开它之间的延迟，而那正是这段宽限期存在的情形。

## Consequences

- 为一部暂时离开的手机提出的提问，现在能活过一次重连。手机本来会失去的认领以它自己的状态被重放，并可通过 `question.answer` 作答。
- `continued` 认领不再以 `open` 重放。在宿主前台等待结束之后重连的手机看到的是它作答路径所要求的状态，而不是一张承诺着宿主并未在服务的等待的卡片。
- approvals 行为不变：最后一次离开仍然执行 `abandonAll()`，因为被卡在决定上的工具没有迟作答路径，也没有任何回来的理由。
- 释放日志行现在标记的是宽限期的结束，而不是那次离开。离开本身不新增日志，需要知道离开时刻的运维读它上面那行连接关闭。
- 宽限期内卸载的桥立即释放且不留定时器：`dispose()` 先清掉宽限期再撤回，而被释放的认领不会被释放第二次。
- 认领表仍然一个线协议 id 一条事实，`open` 与 `continued` 两种存活状态都照旧由 `question.list` 报告；列表、作答与结算没有任何变化。

## Testing

`tests/hub.spec.ts` 用 vitest 假定时器驱动宽限期，且只伪造 timeout 那一对，连接心跳仍是真实的 interval，因此一分钟的认领时间不会向一台不在的手机发 ping。用例包括：最后一部手机离开不会撤回认领（它仍被列出、仍被重放）；宽限期内已配对接入会取消释放，认领因此活过宽限期并且仍可作答；到期只释放一次，只留一行释放日志且不剩定时器；`dispose()` 立即释放且不留任何已排期的东西；`continued` 认领以 `continued` 重放；approval 仍在最后一部手机离开的瞬间被放弃。`tests/questions.spec.ts` 里关于释放、让位与重读的用例被重新指向如今存在的两条路径：宽限期到期，以及卸载时的立即释放。

本套件不验证的：真机 iOS 在宽限期内重连，即挂起的应用能否在六十秒内回来并点开通知。那需要真机，而那也正是这段宽限期存在的理由。
