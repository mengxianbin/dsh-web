# Agent Note: SDK cohort 0.2.1-rc.3

Status: implemented

This note owns the 0.2.1-rc.3 move. [SDK cohort 0.2.1-rc.2](2026-10-17-sdk-cohort-0.2.1-rc.2.md) keeps the earlier migration and its rejected alternatives.

## Problem

The main repository and all four satellite repositories declared the 0.2.1-rc.2 cohort while the operator's host runs 0.2.1-rc.3. The new official line adds region-local plugin More menus, preserves an unsent draft across New Session navigation, and changes DeepSeek model listing. A correct adaptation therefore has to cover the main packages, the independently owned satellites, generated market inputs, and the official loader-row namespace rather than editing one dependency literal.

## Decision

The main workspace's consumed `@deepseek-ai/dsh-*` ranges move to `^0.2.1-rc.3`; every family manifest and the scaffold declares `dsh.engines.dsh >=0.2.1-rc.3` with the same host peer. The README badges, CI and release mount pins, workspace package extensions, release-age exclusions, and lockfile move together. Cordis stays `^4.0.5` and schemastery stays `^3.18.5`, which are still the cohort's versions.

The official evidence is [dsh-v0.2.1-rc.3](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-rc.3) and [the rc.2...rc.3 compare](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.2.1-rc.2...dsh-v0.2.1-rc.3). npm serves rc.3 on `next` while `latest` remains rc.2; the operator's installed rc.3 host is the adaptation target. The plugin-manager floor deliberately refuses older hosts instead of claiming compatibility with an unverified one.

The contract audit makes these bounded adaptations:

- The official `dsh-web-app` patch adds `entry-customization`, so the snapshot in `packages/dsh-plugin-manager/tests/bundle-row-id.spec.ts` includes it. The existing Plugins page DOM seat is unchanged.
- `DraftInitializationOptions.whenDraftExists` is optional, `conversation.chat.turnTail` remains, and no family package implements the changed `MessageSubmissionState` or conversation-header owner. The message-edit wiring needs no source change.
- The shell still exports the same eleven frozen platform modules. The skin-center rescan still finds 329 official tokens. Shared provenance comments move, but no speculative runtime or DOM patch is added.

Each satellite owns and validates its own cohort change: dsh-skins `d37711f`, dsh-pet `26136ed`, dsh-presets `88e508e` merged through [dsh-presets PR #3](https://github.com/zhu1090093659/dsh-presets/pull/3) as `f491e89`, and dsh-community-plugins `42cad66`. All four commits are available on their respective remote `main`, and the main repository's gitlinks name those commits. No package version changes and no npm publication occurs.

The aggregate, shared copies, committed `lib/` artifacts and fingerprints, and market inputs are regenerated through their owning tools. Main-repository changes remain local to `dev`; the required satellite commits are published to their own remotes before the gitlinks move.

## Alternatives considered

**Advance only the main repository.** Rejected: the operator explicitly included the satellites, and the market build reads their pinned content. Their manifests, contracts, and verification therefore move in their own repositories instead of receiving unowned edits in the main tree.

**Stay on rc.2 because npm `latest` has not advanced.** Rejected: the requested and installed host is rc.3, the rc.3 SDK packages exist on npm, and the compatibility floor must name the cohort that actually passed validation. The `next`/`latest` distinction is recorded rather than hidden.

**Modify the linked official DSH checkout or patch around missing APIs.** Rejected: the official checkout is read-only comparison evidence only. Development types resolve from published npm SDK packages, and the rc.3 typecheck found no removed family API requiring a workaround.

**Turn the compatibility update into a release.** Rejected: no release was requested. Family versions stay at 0.4.8, and no tag or npm publication is created.

## Consequences

- The main lockfile's four remaining `>=0.2.1-rc.2` host peers belong to the currently published satellite npm artifacts, not to their updated source repositories. They remain correct until those artifacts are superseded by a later release; the gitlinks and market inputs name the new source commits.
- The plugin manager now requires rc.3 for future family artifacts. Hosts still on rc.2, including the current npm `latest` line, receive a deterministic compatibility refusal rather than an untested install.
- The rc.3 contract itself requires no runtime JavaScript migration: its changes are manifests, compatibility snapshots, tests, provenance, generated artifacts, and documentation. Validation additionally exposed and fixed a pre-existing Windows-only `DeviceRoster` concurrent-write race; that separate fix is recorded in [Serialize device-roster writes on Windows](../bug-fix/2026-10-24-remote-bridge-roster-write-serialization.md). Existing historical release notes, fork provenance, and `docs/archive/` records stay unchanged.
- The cohort also removed the `@deepseek-ai/dsh-tool-subagent-control/list-agents` subpath export (the package now exports only `.`), and the liangshen preset still declared that row, so its sessions failed to mount until the row was deleted. That adaptation, and the three other fixes of the same day, are owned by [issue batch 1937-1942](../bug-fix/2026-10-24-issue-batch-1937-1942-fixes.md).
- The running user DSH service is never restarted or interrupted by this work. Validation uses isolated homes and processes; loading newly built local artifacts into an existing service requires the operator to restart it.
