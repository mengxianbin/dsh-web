# Agent Note: SDK cohort 0.1.7-rc.1

Status: implemented

## Problem

集成分支声明的是 `0.1.7-alpha.2`，而官方家族已经走到首个发布候选版本 `0.1.7-rc.1`（发布于 2026-09-23T13:30Z，npm dist-tag 为 `next`；已发布的 `latest` 稳定版仍是 `0.1.5-rc.3`，`alpha` 标签仍指向 `0.1.7-alpha.2`）。停在原地会带来三个问题：

- 运行中的宿主与每个本地 profile 都必须留在 alpha 线，家族机器可读的宿主下限因此会指向一个不再收到修复的宿主，桌面运行时 pin 也会让基于该分支构建的安装包发出 alpha cohort。
- README 的宿主徽章已经落后一个 cohort —— 在 alpha.2 升级之后它仍渲染 `DSH >=0.1.7-alpha.1`，也就是说这次改动开始之前，唯一面向用户的版本要求陈述已经是错的。
- `0.1.7-rc.1` 正是把「插件与运行时兼容性」变成官方产品行为的版本：声明了不满足当前运行时的 `@deepseek-ai/dsh` peer 区间的插件，会在安装与启动时被拒绝，并给出类型化的拒绝原因与按精确版本的豁免。家族自己的预检查读的是 `dsh.engines.dsh`，两条规则必须在同一次改动中对齐，而不是放任它们互相矛盾。

## Decision

整个 cohort 一次性迁到 `0.1.7-rc.1`，在基于 `origin/dev` 的隔离工作树 `sdk/0.1.7-rc.1` 中进行，因此共享检出与正在运行的 GUI 在集成之前不受影响。

### 一个家族，一个发行版

23 个 manifest 中的 272 个 `@deepseek-ai/dsh*` 规格符、20 处 `dsh.engines.dsh >=0.1.7-rc.1` 下限以及同字面量的宿主 peer 声明、插件脚手架、根 `pnpm-workspace.yaml`（发布年龄豁免账本现为 72 条，两个 `packageExtensions` 键随 cohort 重新取键）、`desktop/runtime/host/package.json` 的桌面宿主载荷 pin 及其重新生成的 hoisted 锁、CI 与发布的挂载冒烟 pin、`shared/web-platform.ts`、`shared/tests/web-platform.spec.ts` 与 `tests/e2e/mount.e2e.ts` 中的 cohort 版本字面量、`scripts/rollout-verify.test.mjs` 的下限断言，以及 `docs/publish-prep.md`、`docs/plugins.md`、根 README 与四个声明了版本要求的包 README 中的 cohort 叙述，一起移动。支撑 pin `@deepseek-ai/cordis 4.0.4` 与 `@deepseek-ai/schemastery 3.18.4` 不动：两个包都没有 `0.1.7-rc.1`，且 cohort 自身的 peer 区间仍然指向它们（`~4.0.4`、`~3.18.4`）。

### 官方变更记录

增量是 `dsh-v0.1.7-alpha.2...dsh-v0.1.7-rc.1`：156 个提交。compare 的 `files` 数组上限为 300 条且不支持分页，因此改为分页读取提交列表（`per_page=100`，两页）并分别读取每个 release body；rc.1 的正文聚合了自 `0.1.5-rc.3` 以来的全部内容，因此会把仓库在 alpha.1、alpha.2 已经适配过的功能再列一遍。

rc.1 中真正新增的面向用户的增量很小：由 `agentTeam` 投影驱动的 Agent Team 面板；插件页新增逐插件配置、registry 探测与 GitHub 镜像恢复；官方插件/运行时兼容性预检；内置 LibreOffice Kit；本地图片灯箱与悬停预览；四种工作详情档位与工具准备进度；PTC 运行时改名与独立进程的 Node PTC；Ralph 默认关闭并移除 E2B 后端；`spawn_teammate` 统一。

比较已发布产物而非版本号（177 个包在两个 cohort 版本都存在；仓库引用的其余 15 个 `@deepseek-ai/*` 名字属于其他版本线）：

| 删除的公开符号 | 无 |
| 改名的公开符号 | 无 |

唯一不向后兼容的改动是两处 interface 改为 type alias（`ToolCallOwnerProps`、`RunningToolCall`）。本仓库没有任何包导入 `@deepseek-ai/dsh-client-ui-tool`，也没有任何源文件引用 `RunningToolCall`、`ConversationStartMatch`、`ToolCallOwnerProps` 或 `ToolCallPhaseProps`，因此应用源码无需改动；`pnpm typecheck` 在 21 个 workspace 工程上通过。打包缺陷账本之所以移动，只是因为它的 `packageExtensions` 键带有 cohort 版本。

### 唯一被适配的表面：真实启动规格的宿主解析

`@deepseek-ai/dsh-agent-preset-registry@0.1.7-rc.1` 新增了对 `@deepseek-ai/dsh-app-boot` 的依赖，因此本 cohort 第一次把一份 `app-boot` 副本拉进 workspace 依赖树。仓库保持 `autoInstallPeers: false` —— 宿主 peer 在运行时由 DSH profile 树解析，`pnpm peers check` 按设计会报告大量缺失 peer —— 于是这份副本能被解析，却无法导入自己的宿主面（`dsh-home-paths`、`cordis-plugin-group`、`dsh-launch-environment`）。`packages/dsh-web-all/tests/shell-isolation.spec.ts` 解析它找到的第一份 `@deepseek-ai/dsh-app-boot`，因此选中了这份不可用的副本，把八个真实启动规格从「使用已安装宿主」变成了红灯。该规格现在只接受「自身声明的全部非可选 peer 都能解析」的候选，从而继续选中它本意使用的已安装宿主权威，在没有安装宿主的检出里依旧以说明跳过。workspace 依赖图未做任何改动：缺失的 peer 是既定策略，不是需要新增宿主面来修补的缺陷。

### rc.1 宿主探针

需要真实 rc.1 客户端才能闭环的重叠决策，用一个真实 `dsh web` 0.1.7-rc.1 宿主的无头探针收敛：scratch `DSH_HOME`，其 profile 选择与本地 profile 相同的 `@deepseek-ai/dsh-base` + `@deepseek-ai/dsh-web-app` bundle，在 OS 分配端口启动并用 Playwright 打开。该组合包含 `plugin-manager`、`ui-plugin-manager` 与 `tool-plugin-manager` 三行；插件页渲染出「Add and manage plugins」、**Add plugin** 操作、官方 registry 选择器，以及 Agent Teams、语音输入、Shell、Agent loop、Subagent、Web search 的逐行配置，控制台与页面均无报错。再用已发布的 registry 聚合包（`dsh plugin --profile web add @linxin666/dsh-web-all@0.3.24`）填充第二个 scratch profile 后，同一页面把它列在 Installed 之下，说明官方安装路径在本 cohort 上端到端可用。该 registry 探针的早前一次运行曾出现 `list slot "conversation.chat.turnTail" requires options.id`，之后未复现，且官方 `turnTail` 槽位在本仓库中不存在，故记为上游问题而非归因于家族。

### 重新生成的官方表面

- **Token 契约。** `scripts/official-tokens-snapshot.mjs` 读取两个已安装的官方表面，把契约从 293 个名字推进到 299 个：新增六个 `--dsw-alias-file-diff-{added,deleted}-{bg,gutter,marker}` 角色，无一删除。`contractVersion` 保持 1，因为这是零删除的纯增量覆盖，没有消费者需要迁移分支。皮肤中心的 fallback 守卫无需新增排除即可派生这些新角色。
- **浏览器平台种子。** rc.1 shell 的冻结模块表与 alpha.2 逐字节相同，因此 `shared/web-platform.ts` 保留原来的九个规格符，只移动验证注释。
- **宿主徽章。** 根 README（中英文）现在渲染 `DSH >=0.1.7-rc.1`，修复了上一次升级遗留的漂移。

在适配之前，已把该 cohort 新增的官方能力与每个家族包逐一比对：

没有任何家族包实现了该 cohort 新增的能力，因此没有删除任何实现，也没有造成能力回退。该 cohort 的新功能也没有被采纳为仓库行为：它们是随宿主一同到来的原生产品面，仓库在这次改动中的职责是不再挡在它们前面。

## Alternatives considered

**停在 `0.1.7-alpha.2`。** 否决：宿主已在同一线上发布了发布候选版本，徽章已经落后于声明的下限，而 `0.1.7-rc.1` 正是家族下限所喂养的官方兼容性策略开始被强制执行的版本；停在原地等于声明一个没有受支持宿主会执行的要求。

**等待 0.1.7 稳定版。** 否决，那是另一个更晚的决定：`next` 标签承载的就是 `0.1.7-rc.1`，而用户点名了这个 cohort；稳定化是独立的发布决策，不是适配该线的前提。

**只改 manifest 与锁文件。** 否决：下限、徽章、CI 挂载 pin 与桌面运行时 pin 是同一份契约，把桌面 pin 落下会让下一次桌面构建发出割裂的运行时。

**让 `@deepseek-ai/cordis` 与 `@deepseek-ai/schemastery` 随 cohort 一起移动。** 否决：两个包都没有发布 `0.1.7-rc.1`；它们各自独立成线，且 cohort 自身的 peer 仍然约束它们。

**因为官方预检已经判断同一个问题，就删除 `dsh-plugin-manager` 的兼容性预检查。** 本次改动中否决：两条规则读的不是同一个字段，官方 UI 不展示版本要求，而证明官方在 npm 发布版 web 运行时上确实拒绝所需的 rc.1 GUI 现场证据，只有在结束本次工作会话的宿主切换之后才能取得。因此把该决定连同明确的后续项记录下来，而不是盲目执行。

**删除网关的安装/移除回退。** 基于同样的证据缺口否决，并且存在真实的能力风险：该回退是安装器 RPC 缺席的运行时上唯一的安装路径，在 GUI 确认官方通道可用之前删除它，等于用一次能力回退换取消除重复。

## Consequences

- 声明的下限、宿主 peer、徽章、CI/发布挂载 pin 与桌面运行时 pin 全部指向 `0.1.7-rc.1`。桌面安装包必须用移动后的 pin 重新构建，用户才会拿到该 cohort；在那之前，pin 的改动只是仓库事实，不是已发布的运行时。
- `@deepseek-ai/*` 影子副本仍解析 alpha 线的本地 profile 必须刷新，而这需要先停止 profile 实例。cohort 检查与刷新步骤记录在升级报告中；在操作者重启之前，运行中的 GUI 继续提供 alpha.2 构建。
- README 徽章不再被允许落后：它与宿主下限说明所拥有的六表面契约同属一体，本次改动修复了它第一次落后的情形。
- 在新 cohort 上执行 `pnpm install` 需要临时把旧 cohort 加回发布年龄豁免，才能通过 pnpm 对陈旧已提交锁文件的供应链检查；解析完成后这些豁免被移除，最终的 `pnpm install --frozen-lockfile --ignore-scripts` 证明该锁文件可以独立通过。
- `desktop/runtime/profile-web` 仍固定 `@linxin666/dsh-web-all` 0.3.19，而本仓库已是 0.3.24，且桌面宿主载荷现在内置 0.1.7-rc.1。此处刻意不推进该 pin：0.3.24 是稳定线的构建（仍带 `dsh-better-sidebar@0.19.1`、`dsh-doctor` 与 `dsh-tool-describe-image`，本线已移除），且是为上一个 cohort 发布的；seed 应与「为本 cohort 构建的家族发行版 + 重新生成的 `pnpm-lock.yaml` + 发布年龄账本」一起推进，属于重建宿主 pin 的那次桌面发版工作。
- `dsh-task-board` 的 `localStorage` 规格在 Node 25 下失败（jsdom 的 `window.localStorage` 桥接解析为一个没有方法的对象），在 Node 24 下通过；Node 24 在仓库 engines 允许范围内且 CI 使用的正是 Node 22。这是既有的环境性失败，不是 cohort 回归，因此门禁序列在 Node 24 下运行。

## Testing

最终树在 Node 24 下通过：`pnpm typecheck`、`sync-shared:check`、`skin-center:check`、`community:check`、`libs:check`、`aggregate:check`、`runtime-deps:check`、`emoji:check`、`docs:check`、`i18n:check`、`test:scripts`、`test:standards`、`test:desktop`、`skin-hooks:check`、`build`、`test` 与 `market:check`。`pnpm install --frozen-lockfile --ignore-scripts` 在根目录与 `desktop/runtime/host` 均通过供应链策略。Token 契约已重新生成且 `--check` 干净；浏览器平台种子已对照 rc.1 shell bundle 验证；桌面宿主 pin 由 `scripts/rollout-verify.test.mjs` 对照脚手架下限断言。

以 CI 形式运行 `bash scripts/e2e-mount.sh`（`FAMILY_TGZS_DIR` 指向本检出打出的 tarball）会把聚合包挂载进一个真实的 `dsh web` 0.1.7-rc.1 宿主（OS 分配端口）并做无头渲染：官方宿主帧在 560 ms 内挂载，被排除的外部行均未出现。若不设 `FAMILY_TGZS_DIR`，该 lane 会在本机因一个与本 cohort 无关的既有原因失败 —— registry 上仍有一份等待已退役 `settingsScope` 服务的家族构建，而 CI 步骤打包正是为了绕开这份陈旧产物；alpha.2 宿主在那里同样失败。
