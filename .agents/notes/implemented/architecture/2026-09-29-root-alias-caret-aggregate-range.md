# Agent Note: The root alias follows the release line with a caret aggregate range

Status: implemented

## Problem

The repository root is a thin alias bundle: its patch is the aggregate's generated `web-ui-*` manifest, while every module those rows import resolves from the `@linxin666/dsh-web-all` dependency (the [alias note](../feature/2026-08-30-repo-root-installable-alias.md)). That dependency spec is therefore a compatibility contract between a patch and a set of exported subpaths, and issue #1442 is what its drift costs: the root declared `^0.3.6`, the git ref moved to a patch whose rows mount family subpaths, a lockfile kept the older child (0.3.10 in the report), and every row failed with `ERR_PACKAGE_PATH_NOT_EXPORTED` — the loader entered recovery mode.

The first fix pinned one exact released version (`0.3.20`): no range, so no older child could satisfy it. It also left the root manifest carrying a hand-maintained literal that only the release gate remembers to move, and it held the root on a single patch of the release line after newer patches had published.

## Decision

- Root `package.json` declares `"@linxin666/dsh-web-all": "^X.Y.Z"`, where `X.Y.Z` is the release tag: the release-line caret whose base is the release the shipped patch was generated by.
- `scripts/lib/root-alias-pin.mjs` asserts exactly that shape against the tag (`rootAggregatePinMismatch`), and `scripts/verify-version.mjs` runs it before publishing, so the base cannot trail the tag and no other form — an exact pin, `~`, `>=`, `*` — passes the release.
- The release bump moves the base with the tag: step 1 of [dsh-web-release](../../../skills/dsh-web-release/SKILL.md) rewrites the root `version` and this dependency together, then refreshes the lockfile specifier.

The caret keeps #1442 closed because the base is the tag: every family release changes the spec string, so a lockfile recorded for the previous release stops satisfying it and re-resolves. What #1442 proved unsafe was a range whose base stayed behind the shipped patch, not a range as such.

## Alternatives considered

- **Keep the exact pin** (the superseded 2026-09-10 decision, commit `058c981c`). Rejected: it writes the version into the manifest as a literal that only the release gate keeps honest, and it drops the root off the release line as soon as newer patches publish. The invariant worth enforcing is "the base equals the tag", which the caret states directly.
- **Keep the wide range and add a runtime guard** that fails early when the resolved aggregate lacks a subpath. Rejected: it converts a boot failure into a slightly earlier boot failure and still leaves lockfiles resolving an incompatible child.
- **A static floor, `>=0.3.19`** (the first version exporting every row then current). Rejected: it forces lock re-resolution once and then silently drifts the moment a family adds a subpath, which is exactly how #1442 appeared.
- **Ship the built aggregate inside the root git payload.** Rejected: it contradicts the alias design (a thin manifest whose modules come from npm) and would duplicate the release build on user machines or in git.
- **Declare no aggregate dependency and let the profile install it.** Rejected: the rows would then have no installed module to resolve, and asking the user to add the aggregate separately restores the duplicate-row conflict between alias and aggregate that the alias note already documents.

## Consequences

- A release moves the range base, so the root follows patches inside the release line while the patch and the modules still come from one release (the npm lane lag excepted).
- A fresh install resolves the newest aggregate in the line rather than exactly the tag's build. Family rows are additive and a removed subpath stays in the aggregate's exports map as `tombstones:` (the [family-satellite note](2026-09-23-family-satellite-repositories.md)), so a newer aggregate in the same line still exports every row an older patch mounts; the dangerous direction is an older aggregate, and verify-version now rejects it.
- Forgetting the base bump is still a release failure rather than a user-visible boot failure: `verify-version` annotates `package.json` and exits 1.
- The npm lane lag described in the alias note still applies: a git install of a commit whose patch references not-yet-published members resolves only after that release publishes.

## Testing

- `node scripts/verify-version.mjs 0.4.4` prints `[verify-version] all 16 packages, the root version and the root aggregate caret ^0.4.4 match v0.4.4`; the same command against `0.4.5` exits 1 and annotates `package.json` with `root dependency @linxin666/dsh-web-all ^0.4.4 does not match tag v0.4.5 (expected ^0.4.5)`.
- `node --test scripts/root-alias-pin.test.mjs` accepts `^0.3.20` on tag `0.3.20` and rejects the exact pin `0.3.20`, the trailing base `^0.3.19`, the old wide range `^0.3.6`, `~0.3.20`, `>=0.3.20`, `*`, and a missing dependency.
- `pnpm install --lockfile-only --ignore-scripts` rewrites one lockfile line (`specifier: ^0.4.4`, still `version: link:packages/dsh-web-all`), so the in-checkout workspace link is unchanged.
