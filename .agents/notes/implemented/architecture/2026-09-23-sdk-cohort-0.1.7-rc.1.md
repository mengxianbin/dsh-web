# Agent Note: SDK cohort 0.1.7-rc.1

Status: implemented

## Problem

The integration line declared `0.1.7-alpha.2` while the official family had reached its first release candidate, `0.1.7-rc.1` (published 2026-09-23T13:30Z, npm dist-tag `next`; the published `latest` stable is still `0.1.5-rc.3` and the `alpha` tag still names `0.1.7-alpha.2`). Three problems followed from staying put:

- The running host and every local profile had to stay on the alpha line, so the family's machine-readable floor would require a host that no longer receives fixes, and the desktop runtime pin would ship the alpha cohort in any installer built from the branch.
- The README host badge had already drifted one cohort behind — it still rendered `DSH >=0.1.7-alpha.1` after the alpha.2 bump —
  so the one user-facing statement of the requirement was wrong before this change started.
- `0.1.7-rc.1` is the release that turns plugin/runtime compatibility into official product behaviour: a plugin whose declared `@deepseek-ai/dsh` peer range does not satisfy the running runtime is denied at install and at boot, with typed refusal reasons and per-exact-version exemptions. The family's own pre-check reads `dsh.engines.dsh` instead, so the two rules had to be reconciled in the same change rather than left to disagree.

## Decision

The whole cohort moves to `0.1.7-rc.1` in one change, in the isolated worktree `sdk/0.1.7-rc.1` based on `origin/dev`, so the shared checkout and the running GUI are untouched until integration.

### One family, one release

272 `@deepseek-ai/dsh*` specifiers across 23 manifests, 20 `dsh.engines.dsh >=0.1.7-rc.1` floors plus the identical host peer declarations, the plugin scaffold, the root `pnpm-workspace.yaml` (release-age exclusion ledger, now 72 entries, and the two `packageExtensions` keys re-keyed to the new cohort), the desktop host payload pin in `desktop/runtime/host/package.json` together with its regenerated hoisted lock, the CI and release mount-smoke pins, the cohort-version source literals in `shared/web-platform.ts`, `shared/tests/web-platform.spec.ts` and `tests/e2e/mount.e2e.ts`, the `scripts/rollout-verify.test.mjs` floor assertion, and the cohort-version prose in `docs/publish-prep.md`, `docs/plugins.md`, the root READMEs and the four package READMEs that state a requirement move together. The support pins `@deepseek-ai/cordis 4.0.4` and `@deepseek-ai/schemastery 3.18.4` do not move: neither package has a `0.1.7-rc.1`, and the cohort's own peer ranges still name them (`~4.0.4`, `~3.18.4`).

### The official change record

The delta is `dsh-v0.1.7-alpha.2...dsh-v0.1.7-rc.1`: 156 commits. The compare's `files` array is capped at 300 entries and is not paginated, so the commit list was paged (`per_page=100`, two pages) and each release body read separately; the rc.1 body aggregates everything since `0.1.5-rc.3` and therefore re-lists features the repository already adapted at alpha.1 and alpha.2.

The user-facing delta genuinely new in rc.1 is small: the Agent Team panel driven from the `agentTeam` projection; the Plugins page gaining per-plugin configuration, registry probing and GitHub mirror recovery; the official plugin/runtime compatibility preflight; bundled LibreOffice Kit; local-image lightbox and hover preview; four work-detail modes with tool preparation progress; the PTC runtime rename with out-of-process Node PTC; Ralph disabled by default and the E2B backend removed; `spawn_teammate` unification.

The packaging-defect ledger moves only because its `packageExtensions` keys carry the cohort version.

### The one adapted surface: the real-boot spec's host resolution

`@deepseek-ai/dsh-agent-preset-registry@0.1.7-rc.1` gained a dependency on `@deepseek-ai/dsh-app-boot`, so this cohort pulls an `app-boot` copy into the workspace tree for the first time. The repository keeps `autoInstallPeers: false` — host peers resolve from the DSH profile tree at runtime, and `pnpm peers check` reports many missing peers by design — so that copy resolves while being unable to import its own host faces (`dsh-home-paths`, `cordis-plugin-group`, `dsh-launch-environment`). `packages/dsh-web-all/tests/shell-isolation.spec.ts` resolved the first `@deepseek-ai/dsh-app-boot` it could find and therefore selected the unusable copy, turning eight real-boot specs red where they had previously resolved the installed host. The spec now accepts only a candidate whose own non-optional peer declarations all resolve, so it keeps selecting the installed host authority it was written for and still skips with a note in a checkout that has none. The workspace dependency graph is unchanged: the missing peers are the documented policy, not a defect to patch with new host faces.

### The rc.1 host probe

The overlap decisions that needed a live rc.1 client were closed with a headless probe of a real `dsh web` 0.1.7-rc.1 host: a scratch `DSH_HOME` whose profile selects the same `@deepseek-ai/dsh-base` + `@deepseek-ai/dsh-web-app` bundles the local profile selects, booted on an OS-assigned port and opened with Playwright. That composition carries the `plugin-manager`, `ui-plugin-manager` and `tool-plugin-manager` rows, and the Plugins page renders "Add and manage plugins" with an **Add plugin** action, the official registry selector and per-row configuration for Agent Teams, voice input, shell, agent loop, subagent and web search, with no console or page error. Seeding a second scratch profile from the published registry aggregate (`dsh plugin --profile web add @linxin666/dsh-web-all@0.3.24`) makes the same page list it under Installed, so the official install path works end to end on this cohort. One earlier run of that registry probe surfaced `list slot "conversation.chat.turnTail" requires options.id`; it did not reproduce, and the official `turnTail` slot appears nowhere in this repository, so it is recorded as an upstream gap rather than attributed to the family.

### The regenerated official surface

- **Token contract.** `scripts/official-tokens-snapshot.mjs` reads the two installed official surfaces and moves the contract from 293 to 299 names: six additive `--dsw-alias-file-diff-{added,deleted}-{bg,gutter,marker}` roles, none removed. `contractVersion` stays 1 because the change is additive coverage with zero removals, so no consumer needs a migration branch. The Skin Center fallback guard derives the new roles without an exclusion change.
- **Browser platform seed.** The rc.1 shell's frozen module table is byte-identical to the alpha.2 one, so `shared/web-platform.ts` keeps its nine specifiers and only its verification comment moves.
- **Host badge.** The root READMEs (Chinese and English) now render `DSH >=0.1.7-rc.1`, repairing the drift left by the previous bump.

## Alternatives considered

**Stay on `0.1.7-alpha.2`.** Rejected: the host had already published a release candidate on the same line, the badge already trailed the declared floor, and `0.1.7-rc.1` is where the official compatibility policy that the family's floor feeds into becomes enforced, so the repository would declare a requirement no supported host enforces.

**Wait for a 0.1.7 stable.** Rejected as a different, later decision: the `next` dist-tag carries `0.1.7-rc.1` and the user asked for this cohort by name; a stable promotion is a separate rollout decision, not a precondition for adapting the line.

**Bump the manifests and lockfile only.** Rejected: the floors, the badge, the CI mount pins and the desktop runtime pin are one contract, and leaving the desktop pin behind ships a split runtime in the next desktop build.

**Move `@deepseek-ai/cordis` and `@deepseek-ai/schemastery` with the cohort.** Rejected: neither package publishes a `0.1.7-rc.1`; their lines are independent and the cohort's own peers still constrain them.

**Remove `dsh-plugin-manager`'s compatibility pre-check because the official preflight now decides the same question.** Rejected for this change: the two rules do not read the same field, the official UI shows no requirement, and the live rc.1 GUI evidence needed to prove the official refusal on the npm-published web runtime only becomes available after the host switch that ends the working session. The decision is recorded with a named follow-up instead of executed blind.

**Remove the gateway install/remove fallback.** Rejected on the same evidence gap, plus a real capability risk: the fallback is the only install path on a runtime whose installer RPC is absent, and removing it before the GUI confirms the official channels answer would trade a duplicate for a regression.

## Consequences

- The declared floor, the host peer, the badge, the CI/release mount pins and the desktop runtime pin all name `0.1.7-rc.1`. A desktop installer must be rebuilt from the moved pin before users receive the cohort; until then the pin change is a repository fact, not a shipped runtime.
- Local profiles whose `@deepseek-ai/*` shadow copies still resolve the alpha line must be refreshed, and that requires stopping the profile instance. The cohort check and refresh procedure are recorded in the upgrade report; the running GUI keeps serving the alpha.2 build until the operator restarts it.

- The README badge is no longer allowed to lag: it is part of the same six-surface contract the host-floor note owns, and this change repairs the first case where it did.
- `pnpm install` at the new cohort needed the temporary release-age exclusion of the outgoing cohort to pass pnpm's supply-chain check on the stale committed lock; the exclusions are removed again after resolution, and the final `pnpm install --frozen-lockfile --ignore-scripts` proves the lock passes on its own.
- `desktop/runtime/profile-web` still pins `@linxin666/dsh-web-all` 0.3.19 while this repository ships 0.3.24, and the desktop host payload now bundles 0.1.7-rc.1. The pin is deliberately not advanced here: 0.3.24 is the stable line's build (it still carries `dsh-better-sidebar@0.19.1`, `dsh-doctor` and `dsh-tool-describe-image`, which this line removed) and was published for the previous cohort, so the seed must advance together with a family release built for this cohort, its regenerated `pnpm-lock.yaml` and its release-age ledger — work that belongs to the desktop release that rebuilds the moved host pin.
- `dsh-task-board`'s `localStorage` specs fail under Node 25 (the jsdom `window.localStorage` bridge resolves to an object without methods) and pass under Node 24, which the repository's engines allow and CI uses; that is a pre-existing environment failure, not a cohort regression, and the gate sequence was run under Node 24 for that reason.

Run without `FAMILY_TGZS_DIR` the lane fails on this machine for a pre-existing reason unrelated to the cohort — the registry still serves a family build that waits for the retired `settingsScope` service, which is exactly the staleness the CI step packs around; the alpha.2 host fails the same way there.
