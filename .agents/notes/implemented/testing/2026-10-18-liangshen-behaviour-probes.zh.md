# Agent Note: 行为探测度量过程，而不只是分数

Status: implemented

与[就地维护的调度规则](../architecture/2026-10-18-liangshen-dispatcher-rules-maintained-in-place.zh.md)配对，后者正是它存在要检验的对象；在[请求面目录与评测工具](2026-09-13-liangshen-request-surface-catalog-and-eval-tooling.md)之上扩展。

## Problem

本包已经在跑 live 矩阵，它自己的报告得出了一个看起来站得住的结论：五臂、15/15 通过、「人格没有可测收益」。样本是每臂三个任务、一次重复（报告自己也标了），而它采的每一个指标都是结果指标——通过率、工具调用、token、花费、耗时。

这个组合看不见本模式真实的失效。一个会话可以每个任务都通过，同时对一个欠明确的规则取了最严解读、把每周期额度花在不可能失败的检查上、让低优先级积压一路升级、并且自己心算调用预算直到没东西可提交。这些都不会移动通过率；而它们恰恰是「能用的调度者」与「看起来能用的调度者」之间的差别。这个形态的证据来自本仓之外，而它令人不安的地方值得记下来：同一个会话在标准任务上得分也高，所以一个由标准任务组成的基准会把它判为合格。

矩阵也没有办法说明一次探测意味着什么。没有 oracle、没有一对脚本策略，「模型拿了 60 分」完全无法说明 60 落在环境所允许区间的好端还是坏端。

## Decision

四个小的确定性环境，每个对应一种行为，各自附带 oracle 与两条脚本策略，位于 `packages/dsh-liangshen/tools/probes/`。

- **prior-override** — 一个路口模拟器，规则写「每周期最多 2 次检查」。模拟器数的是检查调用，因此一次调用带三个动作是合法的，能放行三辆。读成「2 个动作」最多放行 8；花一次调用去验证这个读法能到 12。探测判结果，并记录这个读法有没有被验证过。每周期只允许一次放行——少了这个上限，会话可以再开第二批，不做任何验证就摸到天花板；这正是探测第一次跑真实会话时发生的（得分 24）。
- **refresh-quota** — 一个发布调度器，每周期两次试算、逐周期重置。拿整批积压去试必然冲突、什么也学不到，这一周期就耗在观望上；一小批能暴露车道规则，三个作业放得下。记录放行数、观望周期与额度利用率，因此「囤积」与「无信息的检查」可以区分开。
- **oncall-backlog** — 十二条告警、每步处理两个、共十步，其中 P3 若没人看就升级。按严重度优先扫完会得到干净的 P1 板与 6 次升级；按截止时间优先扫完是 0 次。这是唯一一条有直接行为靶点的规则改动：每轮扫描。
- **budget-ledger** — 二十个服务、一个故障、十二次调用，且每个结果都印出真实的已用/剩余。全量扫不完；四条调用就能摸到故障。记录有没有提交、提交时还剩多少。

`tools/probe-selftest.mjs` 把两条脚本策略各自跑过每个环境，断言好的那条通过、坏的那条失败、被点名的指标朝既定方向移动。它不花钱、几秒跑完，因此「无法区分的探测」在任何模型被收费之前就被抓住。`tests/probe-selftest.test.ts` 把它包成门禁。

语料是 `tools/tasks/liangshen-v41-probes.json`，其任务用 `from`（一个目录加支撑文件，被物化进工作区）取代内联 `files`——探测是一支小程序，塞进 JSON 会变得不可评审。任务还可以带 `metrics`：与 `check` 同样的程序形态，打印一个 JSON 数字对象，记录在判定的旁边，并由 `benchmark-report.mjs` 按组聚合成单独的表格。两列刻意分开——探测的意义就在于它们可以不一致。

在 DSH 0.2.1 下，任何探测要能跑起来都需要 runner 的两处修复，两处都记在这里，因为「静默记下四个失败会话」与「四个探测都失败」读起来一模一样。变体 patch 不再禁用 `headless-startup`：它发布 `headlessStartup` 供 `sandbox-policy` 与 agent 平面各行 inject，禁用它会让所有依赖行永远等一个再也出现不了的服务，preset 根本挂不上。patch 还重新启用了 `credentials` 行——0.2.1 在 headless bundle 里禁用了托管凭据库，于是每个请求立刻鉴权失败。两行修正之后，出厂臂能跑完一个真实会话（4 次工具调用、实际写出一个文件、91,941 token），而不是 1.8 秒返回、用量为零。

`benchmark-live-run.mjs` 另外获得 `--route provider/model[/effort]`。默认仍是固定 route，好让聚合对比仍按每份报告一条 route 来读；探测跑可以点名运维者真正在用的那条 route，而只有它才能说明该运维者会话里的事。

## Alternatives considered

- 整体移植那份外部驾驶基准。否决：它的环境奖励激进试错，把这个激励搬进来等于拿一套本模式并不在玩的游戏来量它。每个探测只隔离一种行为，其 oracle 的两端都可计算。
- 从推理文本里判行为。否决：持久会话日志并非总带推理正文（provider 可能只存签名块与空正文），而能留下来的措辞计数可能与行为方向相反——「let me check」上升的同时真实检查下降。
- 扩展现有的标准任务矩阵。否决：标准任务恰恰被实测证明看不见这些。它们保留，作为对照。

## Consequences

- 本模式有了四个带数字的行为靶点，一次规则改动可以按「它本该移动的那个数字」评判，而不是按本来就 100% 的通过率。
- 每臂每重复多四个 live 会话；探测很小，整轮的成本远低于矩阵里的一行。
- 探测是确定性且离线的，因此 oracle 的回归由免费门禁拦住，而不是一次付费运行。
- 接受一项风险：探测环境由编写规则的同一个仓库编写，因而可能被放宽。防御手段是那条脚本化的坏策略——它必须持续失败。
- `--route` 只能点名 headless 组合注册过的 provider。只有 web profile 挂载的 provider 会无声失败：回合照样走完，运行记录里用量为零，于是每个探测都读成失败。看 `totalTokens` 再决定要不要相信一次探测结果。

## Testing

- `node tools/probe-selftest.mjs` —— 四个探测都区分得开（放行 12 对 8；放行 24 对 0；升级 0 对 6；提交 1 对 0）。
- 包内 `pnpm vitest run` —— selftest 门禁，加上既有的矩阵、报告与组合套件。
