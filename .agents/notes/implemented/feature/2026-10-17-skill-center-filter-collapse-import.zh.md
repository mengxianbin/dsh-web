# Agent Note: 技能中心改为收窄、折叠与导入，而不是一次铺满所有行

Status: implemented

## 问题

技能中心把七个来源分组平铺列出，每行都带完整描述、适用场景、可调用标记、
启用开关、编辑入口与删除入口。对单个技能这是合适的行，对六十个技能就是
错误的页面：列表是面板的主要表面，但收窄它的手段只有关键字搜索和工作区
选择，因此在繁忙的目录里找一个技能，意味着要一路扫过用户日常并不打理的
系统内置与运行时条目。

另一半问题在入口。新建技能要逐字段手填；把已经存在于别处的技能搬进来，
只能一个一个重建 SKILL.md，而且没有任何办法让迁移后的副本与其来源保持
一致。

## 决定

- **三个筛选维度叠加在搜索框之上。** 来源分组、启用/禁用状态、行标记
  （「由插件提供」/「无本地文件」/「软链接」）与既有的工作区、关键字维度
  同在 `src/client/skill-filter.ts`。维度之间取交集；同一维度内的多选取并集，
  因此勾两个来源或两个标记是放宽结果而不是清空结果。筛选面板收在一个工具栏
  开关之后，开关上显示当前有几个选择在收窄列表，默认视图不会因此变得更密。
- **分组标题就是折叠控件。** 首次使用时只展开项目根与用户根；系统内置、
  自定义目录与运行时分组默认折叠，并在标题上保留行数。折叠时组内行被卸载，
  大目录的渲染也因此更便宜。
- **视图状态属于浏览器。** `src/client/panel-prefs.ts` 用 `localStorage` 持有
  筛选维度与每组折叠决定，因为布局在别的面板占用中栏时会卸载本页：组件本地
  state 会在每次切面板时丢失。存储文档按不可信输入逐字段校验，旧版本写入的
  文档只会丢掉读不出来的那个字段；拒绝存储的浏览器照常工作，只是不记忆。
  折叠按组记录为对默认值的覆盖，因此本版本不认识的来源分组仍按它自己的类别
  决定默认展开或折叠。
- **导入是独立的创建面。** `POST /api/dsh-skill-explorer/import`（`src/import.ts`）
  从用户指名的宿主目录或浏览器读取后以 base64 提交的 `.zip` 批量创建技能。
  候选按扫描所用的同一套接受规则校验（`isSkillName` + `parseFrontmatter`），
  文件原样写入，因此创建表单不认识的 frontmatter 字段
  （`disable-model-invocation`、`user-invocable`、`input` 块）在迁移中得以保留。
- **冲突按官方来源 rank 裁决。** 同名技能若位于更强来源，它就压过目标根，
  导入的文件永远不会是模型收到的那个，因此该候选报告为 `shadowed` 而不写入；
  同级来源意味着该根里这个名字已被占用（`exists`）；更弱的来源被导入压过，
  因此写入。
- **「复制为模板」复用既有的 read 路由。** 行内动作经 `GET /read`（它用最新扫描
  解析该行自己的路径）取回技能，再经面板 controller 把草稿交给创建 tab，
  因为创建 tab 只在被选中时挂载。不需要新路由，且草稿只可能来自面板正在
  展示的技能。

## 导入的边界在哪里

既有写路由的规则没有改变：它们只改写最新扫描为「面板展示过的名字」解析出的
那个路径，因此客户端路径只是身份声明，从来不是位置。导入无法这样做——它创建
的文件还没有被任何扫描见过——因此它获得自己的显式边界，而不是去放宽写路由的：

- 它读取的内容只有 `<目录>/<名>/SKILL.md`、`<目录>/<名>.md`（一层，正是面板
  自身扫描接受的两形态）或提交上来的压缩包；
- 来源目录里的符号链接与点目录被跳过而不跟随，因此导入无法被安插的链接
  引向别处内容；
- 它只以 `O_EXCL` 写入用户根或项目根下的 `<技能根>/<名>/SKILL.md`，从不改写
  已有文件——在名字看起来还空闲时做出的计划，仍然会输给先出现的那个文件；
- 请求有界（压缩包 4MB、512 个条目、单个 SKILL.md 64KB、展开文本 4MB），
  且官方 provider 会丢弃的候选被跳过而不导入；
- 它与家族其余路由同在 loopback 围栏之后，因此目录形态永远只是「提供服务
  这台机器上的一个路径」。

## 为什么压缩包在宿主侧解码

浏览器本可以用 `DecompressionStream('deflate-raw')` 自己解压，但那会把压缩包
格式放到无法脱离 DOM 做单测的那一半，并让 inflate 这一步不可验证。宿主侧
解码意味着由 `node:zlib` 完成解压，读取器是对 buffer 的纯函数，而且接受的
布局（stored、deflate、嵌套路径）与拒绝的布局（zip64、加密条目、未知方法、
越界路径）都针对测试逐字节构造的压缩包验证。代价是这段 JSON 载荷上的 base64
膨胀，而它实际很小。

## 考虑过的替代方案

- **常驻的筛选栏。** 否决：本问题要解决的是密度，而常驻的第二条工具栏会把
  密度重新造出来。开关只花一次点击，并且在存有筛选时自动展开，因此被收窄的
  列表不会无从解释。
- **所有来源分组都保持展开。** 否决：在配置过的安装里，用户不打理的来源
  （系统内置、运行时注册）数量多于他们打理的，全部展开正是 issue 描述的
  那面平铺墙。折叠的标题保留计数，因此没有东西被静默隐藏。
- **把筛选维度与 provider 开关一起存到宿主。** 否决：宿主的存储状态被每个
  浏览器、每台已配对设备共享，而筛选维度是「正在看这个页面的人」的视图偏好，
  不是关于安装的事实。两个窗口也会为同一个值互相覆盖。
- **经由 create 路由逐个导入。** 否决：一次批量导入会变成 N 次往返，且无法
  报告整批的结果；create 路由对已存在的名字回 409，无法区分「同级已存在」
  与「被更强来源覆盖」。
- **扫描来源目录时跟随符号链接。** 否决：面板的扫描跟随链接，是因为链接表达
  用户的挂载意图；而导入是「复制」，跟随链接会把内容静默复制进一个该链接
  目标从未打算到达的根。
- **引入一个 zip 库。** 否决：为一种多年未变的格式写 130 行读取器即可；该依赖
  会成为本包唯一的此类运行时导入，而技能压缩包用到的子集（stored 与 deflate、
  单磁盘、不加密）小到值得自己拥有并测试。
- **提供覆盖被覆盖候选的选项。** 否决：用户将被迫在面板以同一个名字呈现的
  两个技能之间做选择，而 rank 规则已经说明了模型收到哪一个。

## 后果

- 折叠会隐藏仅靠关键字本来能搜到的行。空状态区分「完全没有技能」与「当前
  筛选下没有技能」，且每个折叠分组都声明自己的大小，因此不必翻开每个分组
  也能恢复过来。
- 筛选维度按浏览器配置保存：跨面板重挂载与刷新保留，但不跨浏览器或无痕窗口。
- 导入从不覆盖，因此重新导入一个上游已变更的技能，需要先删除或重命名本地
  副本。这是一次写多个文件的操作刻意付出的代价。
- 使用 zip64 或加密的压缩包会被拒绝而不是部分导入；错误会点名出问题的条目，
  便于用户重新导出。
- `.zip` 读取器与导入规划器是带自己 spec 的一等代码（`tests/import.spec.ts`），
  覆盖来源 rank 表两个方向的失败。
- 面板现在有三个页签级表面（技能、创建、导入）以及一条通往创建表单的复制
  路径。页签与草稿状态仍放在面板 controller 里，理由与中栏家族既有记录一致。
