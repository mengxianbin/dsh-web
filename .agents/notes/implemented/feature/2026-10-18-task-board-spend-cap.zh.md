# Agent Note: 看板派活的每日 token 上限

Status: implemented

## Problem

看板会为一整棵子任务树开启真实的 DSH 会话，而遥控器现在能创建成员卡并在无人值守的情况下把它们跑起来。这一天要花多少钱没有任何边界：一棵失控的树，或者一个不断建卡的遥控器，会一直花到有人注意到账单为止。用户要求把「装闸」和「合闸」分开——代码先落地、上限保持 0 让看板与之前完全一致，真要设数时再设。

计量单位不能是钱。家族的使用账本只对 DeepSeek 官方路由盖 `cost`，其他 provider 一律留 0（该账本由[使用统计](./2026-08-29-usage-statistics-plugin.md)拥有），因此金额上限在恰好路由到别处的部署上会读成「免费」。token 是当天消耗的唯一完整度量。

## Decision

新增一个全局设置键 `spendBudgetTokens`：volatile、默认 `0`、按本地日期计的整数 token。`0` 表示不设闸。它在每次判定时读取而不是被冻结，因此关闸或调高上限会立刻作用于下一次运行，无需重启。

读它的是两道闸，因为进入一次运行有两道门。

动作路径——`HostTaskBoardService.applyBoardAction` 里的 `run` 与 `rerun`，紧跟 Agent Teams 硬闸——以抛出消息拒绝：`spend cap reached: N tokens of M today; raise the cap in the task board settings`。调用方收到的 board-refused 就是这段文本，因此这道闸不引入任何错误码；报告其他所有拒绝的同一条读取路径也会报告它。

定时路径——账本的 `openScheduled`，cron 定时器不经过任何动作就能到达——把同一段文本写进 `scheduler.error`，并把这次触发滚到下一个目标、不消耗规则的运行次数预算。定时触发没有可抛的客户端，而看板对「不能开启的一次触发」本来就有这个契约：写明原因、向前滚动、一次都不花。

## 数字从哪里来

闸门在判定时读取 `$DSH_HOME/dsh-usage/usage-ledger.json`，把今天这个本地日期桶里的 `inputTokens`、`outputTokens`、`cacheReadTokens`、`cacheWriteTokens` 相加。思考 token 不再叠加：它本来就包含在输出计数里，那本账本自己的总量就是这么定义的，因此上限与使用统计面板对「当天花了多少」永远不会给出两种答案。日期键用账本自己的本地日期，两者的零点因此同时翻转。

账本读不到时每进程报告一次，并且不拒绝任何东西。「看不见」不等于「没花」，但另一种做法——因为某个兄弟插件缺席就拒绝每一次运行——会为一条诊断信息把看板卡死，比一个会明说自己测不准的上限更糟。

## 默认 0 就是它出现之前的看板

两道闸都先看上限值再看别的：不打开任何文件、不订阅任何事件、不保留任何计数器、不新增账本字段、不提升 schema 版本。从未配置上限的部署，跑的是没有这项设置时发布的同一条代码路径。

## Alternatives considered

看板自己折叠 `session/event`（使用统计插件用它填自己的账本）能给出即时读数，也没有跨插件的文件依赖。它输在持久性：值只活在内存里，而 Loader 在任何配置改动时都会重挂载行、进程重启也会清空，于是当天的花费会被重置，上限可以靠重启 Host 绕过。要让它持久，就得新增一个自带原子写与损坏处理的状态文件，或者提升看板账本 schema 并连同迁移契约一起改——比这次测量本身要重，还会在同一个进程里出现第二个花费状态的写入者。

金额上限被否掉，因为账本只对 DeepSeek 官方路由计价；见 Problem。

只在启动时拒绝（卡片已经进入运行列之后）被否掉：调用方要求的是执行，需要就那次执行得到一个答案；会话已经存在之后的拒绝是结算问题，不是闸门。

新增一个 `ScheduleStopReason` 取值被否掉。那是持久化词表：联合类型、线上允许清单和三份语言字典都要改，只为让详情页的一行把某个既有原因说成「token 上限」，而 `scheduler.error` 已经带着精确数字。定时跳过因此复用既有的 `limit` 原因，靠调度错误提供精度。

账本读不到时失败关闭（fail closed）被否掉，理由同上：这道闸会让每个没有挂载使用统计插件的部署全部跑不起来。

## Consequences

这道闸计量的是整个 Host 的用量，而不只是看板开启的会话。这是刻意的——针对操作者实际付费的那个账户设一个上限，读的也是使用统计面板显示的那个数字——但这也意味着用户自己聊天聊得多同样会吃掉看板的预算，而只统计看板用量需要它自己维护「会话到执行」的对应关系。

使用统计插件以 3 秒防抖落盘，因此读数最迟落后最繁忙的时刻一个防抖窗口，而窗口内的花费可以在下一次判定看见之前就跨过上限。

这次跳过在规则上记录为 `limit`，而真正的原因在调度错误文本里，所以只看规则存储原因的读者会读到「已达次数上限」，必须再读调度那一行才能看到数字。

这道闸依赖兄弟包在磁盘上的格式。该格式由 `dsh-usage` 拥有；它一旦变化，必须在同一次改动里同步到这个读取器，而没有挂载该插件的部署会得到一个永不触发（并在第一次判定时报告一次）的上限。
