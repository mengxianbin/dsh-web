# Agent Note: 一张锁屏卡排下几个会话

Status: implemented

## Problem

一张锁屏卡只说一个会话（§29）。于是三个会话在跑就是三张卡、三个 APNs 令牌、三块锁屏位置，以及桥每分钟额度里被切成三份的那一段；而手机侧下一轮要把这个上限换成一张卡排下几行。桥当时能发的东西里没有任何一件办得到：`content-state` 只有一个 `phase` 与一句 `statusLine`，而一张没地方说「另外两个还在等你」的卡，只会让用户自己打开 App 去发现。

看上去显然的解法——加一个列出会话 id 的键，让手机自己去读名册——把判断挪到了客户端，客户端于是拥有了「这张卡说的是哪几个会话」的第二个答案。落地的是小的那一半：桥挑行，三件可读的事实按桥给的顺序上线。

## Decision

- 协议 §30（iphone_remote_use_dsh 仓的 `docs/protocol-v1.md`）给 `content-state` 追加一个可选键：`rows`，最多三项，每项 `{name, status, phase}`。`phase` 逐字复用 `content-state.phase` 的四个取值，且不新增方法、能力名、主题、头字段，既有的键一个都不改形，所以 `hello.r.minor` 由 17 升到 18，`hello` 里别的一处都不动。
- 桥一旦说这套协议就始终发这个键。空数组与缺席对手机是同一件事（§30.2），但一个时有时无的键会逼客户端在同一个时刻的两幅画之间做选择。
- `LiveActivityNotifier` 挑行：先提问中的会话，按提问与审批到达的顺序；再正在跑的会话，按宿主的 `updatedAt` 倒序；上限三项，多出来的尾部直接丢弃，不换行也不分页。这个顺序就是 §30.6 故意留给桥的优先级，而等待中的会话排在干活的前面，因为那一行才值得玻璃最上面。
- 一行只带两个活着的相位：`waitingForAnswer` 与 `running`。已经结束或失败的回合是卡片自己的 `phase` 与自己那一句，在那儿说一次就够；再排成一行等于把同一件事说两遍，还会让一张正在离场的卡在走之前长高。
- 挑选读的是单会话状态本来就用的那批事实：需要答复的会话读 `#waiting`，正在干活的读 `#running`，后者由名册的 `agentRunning` 建出来。因此一张卡与它自己的行不会在「哪些会话在跑」上互相矛盾。`ActivityRosterRow` 增加 `title` 与 `updatedAt`，两者本来就在 §9 公布的名册行上。
- `status` 与 `statusLine` 用 App 自己那份英文固定词，一个相位一句——`Running`、`Waiting for your answer`、`Stopped`、`Turn finished`——并且只经一个取用函数（`statusLineOf`），同一个相位在卡上不可能有两种说法。§29.7 把玻璃上的字定成客户端那份固定表；这条通道原先发的中文会在同一张卡上摆出第二种语言，与 App 自己写的 `Running` 打架。提问与审批共用一个等待短语，因为 App 那份表只有一个。`core/push.ts` 的中文通知文案不动：通知是给人按自己的语言读的，卡是 App 自己的面。
- `name` 是宿主自己的标题经 `normalizeActivityRowName` 之后的结果，这条规则只存在这一处，且用的是 App 的 `SessionActivityDisplayName` 同一个判据：尾部括号组的内容是路径或空才摘，括号一起摘，一直摘到不再是这种组为止；`Ship (main)` 是名字的一部分，留着。宿主没闭合的尾部组，含路径才切掉（否则 `Deck (/Users/zcl/code/x` 会把半条路径送上玻璃），不含路径就不动（`Fix it (beta`）。剩下的是压缩过空白、去掉尾边悬挂分隔符与不闭合括号、并裁到行名上限的结果。
- 宿主从未给过标题的会话不产生行。§30.2 要求三个键都非空，§30.4 让手机丢掉没有名字的行，所以桥干脆不写它，卡回落到手机用单会话字段合成的那一行。键本身照发，只是空的。
- §29.4 的去重判据现在包含行，所以行被改名、重排或丢掉都算说法变了，而给标题追加一条路径不算：规整后的名字没变。
- 没有任何客户端连着时，产生本记录用来结卡的那个 `turn/end` 的流，来自[常驻观察者记录](../architecture/2026-10-22-remote-bridge-standing-watchers.md)的决定。

## Testing

单测断言了这个顺序（提问按到达、再按最近更新、上限三行且尾部丢弃）、结束的回合永远不进行（那张卡只在自己的 phase 上说一次 failed 或 ended）、四个相位逐字对应的那一句、真实投递里两个短语字段的纯 ASCII 断言、真实名册造出来的规整用例（绝对路径、全角括号、空括号组、悬挂分隔符、保留 `(main)` 的名字、宿主没闭合的组、超长标题），以及去重：同一份名册不发，只追加路径的改名不发，真的改名发一条并带上新的行。行的形状对着冻结的键序断言，`rows` 排最后，六个 §29 的键因此不会移位；不带 rows 构建出来的卡则根本没有这个键。门禁是 `pnpm typecheck`、`pnpm lint` 与 `pnpm test`。

## Alternatives considered

- **让手机从名册自己造行。** 否掉：这等于把「这张卡说的是哪几个会话」的第二个答案放到客户端，两边任一改动就会分叉。
- **一张卡只排自己那一个会话的行。** 否掉：这保留了「一卡一会话」的模型还为它付字节，而 §30 就是让一张卡成为排下几个会话的地方。
- **只有一行时不发 `rows`**，反正手机合得出来。否掉：合成的那一行用的是卡自己的 `statusLine`，只有那唯一一行正好是卡自己的会话时才成立；显式写出来字节一样、且不需要推断。
- **所有尾部括号组一律摘掉**，于是 `Ship (main)` 会读成 `Ship`。否掉：App 对卡自己的名字只摘路径组或空组，桥侧另立一条规则会让同一张卡上的同一个名字出现两个版本。
- **保留这条通道原先的中文短语表。** 否掉：§29.7 把玻璃上的字定成客户端的英文固定表，中文卡面会在 App 自己写的 `Running` 旁边摆出第二种语言；通知通道保留中文文案，那是给人按自己的语言读的面。
- **把卡片自己的 failed 或 ended 行也塞进 `rows`。** 否掉：卡已经说过那个相位，这一行只是重复，还会让正在离场的卡长高。
- **在手机渲染时清掉路径。** 否掉：§29.5 根本不许路径上线，修法只能在投递之前。
- **加一个 `waitingCount` 或活动会话数。** 按 §30.6 否掉：能从已发键算出来的数字，不占兼容预算的位置。
- **按各 phase 的 relevance 分值排行**（等待 100、失败 90、运行 60）。否掉：relevance 排的是整张卡在锁屏上的位置，那样一个失败会话会压在用户还欠着答复的提问上面。

## Consequences

- 寻址不变：一张卡仍然只指一个会话，不指会话的卡仍然永远推不到（§29.9），`runningCount` 仍然是整座桥的总数。行是内容，不是寻址。
- 每次卡投递最多带三个短字符串，上限丢掉第四个会话，而不是换行或分页。
- 同一时刻所有卡上的行是同一份，且只写谁在等、谁在跑：任何一张卡都不会列出已经离场或已经结束的会话。
- 尾边不是路径的标题（例如 `你是本仓 (/a) 请修`）会把路径留下：规则只摘尾部括号组。要清中间路径得单独决策，因为它开始改写宿主自己的名字。
- 行名上限是桥侧的数字（48 个字符），手机渲染时可能再裁一次。
- 未证明：真实 APNs 投递与真机。测试离线驱动 notifier 与构建函数，验证的是形状与行的选择，不是 App 的 `Codable` 类型解得开——那一半是手机仓里的 §30 变更。
