# Agent Note: 技能中心给插件提供的技能一个启用开关

Status: implemented

## Problem

指令文件来自插件 provider 的技能，在面板里没有可写路径。注册表会报告一个 `SkillSummary.path`，但该文件落在本面板扫描的每一个技能根之外，因此这一行渲染出来没有开关、没有编辑、没有删除，写路由本会返回 404。一个列出了技能、却连它最基本的属性都无法管理的面板，读起来是「坏了」而不是「有边界」——而开关恰恰是最难解释缺失原因的那个控件，因为其他每一行都有它。

同时，也没有任何文件是面板可以改写来记录这个决定的。其他行用的 frontmatter 开关改的是插件拥有的 SKILL.md，位于面板不扫描、也没有文档承诺会写的目录里：那里的 frontmatter 被改坏会坏掉的是 provider 而不是面板，而一次插件升级就可能把这个设置整个丢掉。

## Decision

插件提供技能的开关状态存在面板自己的存储里，键就是面板已经展示的那个身份。

1. **存储。** `provider-toggles.ts` 拥有位于 `$DSH_HOME/dsh-skill-explorer/provider-toggles.json` 的一个 JSON 文档，形状为 `{ version: 1, disabled: [{ name, provider }] }`。键是稳定的 `(provider, name)` 组合：光有名字不够，因为注册表按名字合并，而两个 provider 可以各自为同一个名字提供文件；缺失的 provider 归一化为空字符串，因此同一个技能永远只映射到一条记录。写入是原子的（唯一临时文件、`fsync`、`rename`），被打断的写入不可能留下半份文档。
2. **容错且有界的读取。** 缺失、损坏或外来形状的文档读作「没有技能被停用」——也就是全新安装的状态——而不是让 list 路由失败。名字不符合官方技能语法、或 provider id 超过 200 字符的记录被丢弃而不是继续携带，重复项合并，集合上限 512 条。`setProviderSkillEnabled` 会跳过无变化的写入，因此两个方向都幂等：双击或重试的请求无法堆出重复记录。身份类型只以 type-only 导入，因此存储不会与拥有名字语法的收集器形成运行时循环。
3. **路由。** `POST /api/dsh-skill-explorer/set-provider-enabled` 接收 `{ name, provider?, enabled }`，并用存储自己那道校验检查身份。它从不接收或写入路径：客户端发送的是它展示过的身份，不是位置。**停用**要求一次最新收集仍能把该组合解析成 `provider-file` 行——与文件写路由通过 `resolveScannedSkill` 遵循的同一条「只针对面板展示过的东西」规则，这里用的是身份而非路径——否则返回 404。**启用**只会删除一条记录，因此无条件放行：插件可能在记录仍存着时被卸载，而那条记录必须保持可删除。
4. **收集在最后应用存储。** `collect.ts` 导出 `applyProviderToggles`，为它点名的行清掉 `modelInvocable`，并把它作为 `collectSkills` 的最后一步。最后一步是承重的：注册表合并可能用注册表自己那条无路径的条目替换掉扫描到的条目，因此更早应用存储会让合并顺序决定某一行是否可开关。只有 `provider-file` 行会被触碰——`editable` 行的开关改写的是它自己的 frontmatter、扫描已经反映了它，而 `virtual` 行根本没有文件。与这个开关所代替的 frontmatter 字段一样，它只清 `modelInvocable`；provider 自己的 `userInvocable` 策略并不是模型的自动调用决策，保持注册表报告的样子。
5. **一个开关，两种身份。** 只要一行有路径、或者它是 `provider-file` 行，面板就提供开关；切换时，前者带经认证的路径调用 frontmatter 路由，后者带身份调用面板本地路由。两种无路径状态仍然都不提供编辑与删除，因为那两个控件确实会返回 404。
6. **范围是面板本地，且每个界面都如实说明。** 宿主注册表照旧加载该技能。这个开关改变的是本面板列为可调用的内容，而不是会话能加载什么；要真正把这样的技能从模型那里拿走，要在它的 provider 获取它的那个地方移除或停用它。行提示、包 README（安全模型与已知限制）与包 `AGENTS.md` 都说明这一点，而不是暗示模型已经收不到该技能。

## Scope and boundary

这份存储不是 provider 注册表，不是模型目录的权威，也不是编辑或删除 provider 文件的途径。官方 `skill` 工具目录仍然是「一个会话能加载什么」的权威；面板的目录对齐仍归[The Skill Center Lists What the Official Provider Loads](../bug-fix/2026-10-03-skill-center-lists-official-loadable-skills.zh.md) 所有，有本地文件的技能的调用策略规则归 [Omitted Invocation Fields Mean Invocable in the Skill Center](../bug-fix/2026-10-03-skill-explorer-invocation-omission-means-allowed.zh.md) 所有，本次收窄的无路径行的呈现归 [The Skill Center Manages the Custom Roots the Provider Row Declares](../bug-fix/2026-10-05-skill-center-manages-provider-row-custom-roots.zh.md) 所有。三者都没有被取代。

## Alternatives considered

**照样改写 provider 的 SKILL.md frontmatter。** 否决：面板的全部写入安全属性就是「只改动最新扫描产出的路径」，而注册表报告的路径必须由一次并不存在的扫描重新校验；而且那会让插件升级有能力弄丢这个设置。

**不给开关，让那一行自己解释自己。** 否决：需求就是一个控件。那一行本来就已经区分「由插件提供」与「无本地文件」，把两种状态都留在无控件，正是让一个已列出的技能看起来像坏了的原因。

**只按技能名做键。** 否决：注册表按名字合并，因此两个 provider 可以各自为同一个名字提供文件、而面板只展示其中一行。只用名字会让一个 provider 的记录静默掉另一个 provider 的行。

**用 provider 的文件路径做键。** 否决：那恰好重新引入了本 note 拒绝接受的未经认证路径，而且插件一旦移动或重新打包它的文件，这条记录就失效了。

**把存储放进注册表合并里应用，而不是放在收集末尾。** 否决：合并可能用注册表自己的条目替换扫描条目，于是合并顺序会决定某一行是否可开关——一个排序事实不该有能力改变用户记录下的决定。

**让停用也像启用一样无条件。** 否决：停用记录从下一次 list 起生效，因此无条件的停用记录可以静默掉面板从未展示过的一行。启用只删除记录，没有这类风险，这正是这个不对称是刻意的原因。

**通过官方技能注册表写入这个开关。** 否决：本面板是没有注册表写入面的 GUI 管理层，而注册表级停用是它无权作出的宿主级行为变更。

**把开关放在面板自己的插件 config 里。** 否决：那份 config 与 profile patch、宿主层层叠加，因此写在其中的机器字段是一块共享的、手工可编辑的表面，而不是面板自有状态，而且手改 patch 就会把它抹掉。

**轮询或监听注册表变化并同步到存储里。** 否决：存储只在收集时被读取，因此已经跑过的 list 会在用户做出切换的那一刻就反映它。监听会为一个人只在一处设置的值凭空增加第二个事实源。

## Consequences

- 插件提供的技能可以在面板里停用，且面板自己的列表在下一次读取时就与开关一致：存储按请求读取而非在挂载时捕获，因此切换立即生效，重启也会把存储的集合读回来。
- 开关只是一个视图决定。宿主注册表照旧加载该技能，行提示、README 与包 AGENTS.md 都说明它，因此用户不会把开关读成「模型已经没有这个技能了」。
- 存储归面板所有、可以随手丢弃：删掉该文件会让每个插件提供的技能回到启用，而损坏、外来或超限的文档也降级到同一状态，而不是让 list 失败。
- 面板不再列出的身份仍然可以被启用，因此在它的插件消失之后存储记录依然可删；但它不能被停用，因此存储不会为面板从未展示过的技能增长条目。
- 想要真正把这样的技能从模型那里拿走的用户，必须在它的 provider 获取它的那个地方动手。那是本开关看起来比实际弱的一处，也正是「面板本地」这个范围被写在每一个界面、而不只是写在本 note 里的原因。
- 有界且去重的文档意味着手改过的文件可能损害面板的保真度，但无法无限增长，也不会让存储变得不可读。

## Testing

`packages/dsh-skill-explorer/tests/provider-toggles.spec.ts` 单独覆盖存储：停用一个技能在 DSH home 下恰好留下一条记录、同一技能停用两次仍只有一条记录、把一个切回启用后另一个仍保持停用、重启回来的面板仍看到自己停用的技能、启用一个从未停用过的技能完全不留下文档、损坏的文件读作全部启用、外来的文档形状读作空、匹配不到任何行的记录被丢弃、超限的文档被截断、不符合官方语法的名字不产生记录，以及存储留在插件自己的 home 目录内。`tests/routes.spec.ts` 端到端覆盖路由：下一次 list 把该技能报告为非模型可调用、第二次停用只存一条记录、宿主重启后仍显示为已停用、切回启用恢复可调用视图、对面板不列为插件提供的技能停用被拒绝、对面板已不再列出的技能启用被放行，以及畸形请求返回 400 且不写入。`tests/collect.spec.ts` 覆盖应用这一步：点名 `provider-file` 行的记录会清掉 `modelInvocable`，而点名 `editable` 行、`virtual` 行、未列出的技能、或另一 provider 下同名的记录都不改变任何东西。`tests/panel.spec.tsx` 覆盖渲染：provider 行带开关，而真正无文件的那一行没有；切换 provider 行认证的是它的 provider 身份而不是路径。包测试套件通过（176 项）。
