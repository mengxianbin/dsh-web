# Agent Note: 手机没在场时，桥替它认领那次提问

Status: implemented

## Problem

桥只在至少一台已配对设备在线时才认领提问：`hub.question()` 一旦看到 `pairedClients === 0` 就直接 `next()`，把这道题交还宿主自己的答案链。手机端根本没有后台模式（iOS 客户端是刻意不声明），离开前台几秒就被系统挂起，于是这两件事叠加成了常态：用户不在手机前时产生的提问从未被认领、`question.list` 不会列出它、推送不会发、重连也不会重放。卡片只存在于桌面端，而手机无法回答一道它从未听说过的题。

## Decision

提问到达时若没有任何已配对连接在线，桥**替最近配对过、且仍登记了推送令牌的设备认领**，并立即发出告警推送（`st: "question"`），即使这一次没有向任何连接投递过帧。认领保留 `OFFLINE_QUESTION_CLAIM_TTL_MS`（600000 毫秒，可用 `DSH_REMOTE_BRIDGE_OFFLINE_CLAIM_TTL_MS` 覆盖）。

三条出路共用一个幂等释放入口，因此宿主链至多被启动一次、也不会发第二条通知：手机连上并声明 `questions.v1`（既有重放把卡片交给它）、手机作答、或窗口到期撤销并交还。已配对连接上线但**没有**声明 `questions.v1` 时立刻撤销——§11.3 的判据是“在线却没人能收”，且在 hello 时判而不是只在认领点判，否则一个老客户端会让 agent 等满整个窗口。

APNs 的 `410` / `Unregistered` / `BadDeviceToken` 是“投递失败即吞”的唯一例外：清掉该设备的推送登记，且只有在再没有任何在册设备持有令牌时才释放认领。

审批路径一字未动；没有新增方法、主题或能力名，`hello.r.minor` 停在 18：客户端本来就在每条新连接读 `question.list`、并在声明后接受重放，没有第二条代码路径可供公告去切换。

## Testing

`tests/offline-claim.spec.ts` 共十二条：认领与那一条告警；从未登记过设备时不认领；窗口内手机回来即交付且不重复告警；作答而宿主链从不启动；到期只交还一次；APNs 拒绝唯一令牌、拒绝全部令牌、拒绝两台中的一台；宿主自己结束这道题；无法接收的老客户端；阻塞式提问；以及没有签名密钥的桥什么都不认领。

## Alternatives considered

**保留“只在线认领”，仅补一条通知。** 没有任何认领时发 `st: "question"`，等于告诉用户有一道手机答不了的题，然后把人赶去 Mac：解决了“知道”，没解决“能答”。

**用静默推送唤醒客户端重新认领。** 宿主今天只发告警载荷，iOS 不保证静默投递，唤醒窗口约三十秒。把它当作主机制，等于把特性建在平台唯一不肯承诺的投递路径上。

**两侧同时可见、先答者胜。** 本仓 2026-10-17 正好这么做过，九分钟后回退：宿主的 `user-questions/request` waterfall 没有通道告诉自己的 UI“桥已结算这道题”，桌面持续提供一张已经答过的卡。在宿主长出结算通道前不复用。

**新增能力名并抬 minor。** 客户端不会为此改变行为，收益全落在它本来就做的读取上；没人分支的能力名只是会被误当成行为开关的握手读数。

## Consequences

阻塞式提问现在要等满窗口，宿主自己的 UI 才会拿到它，也就是说 agent 可能白等十分钟去等一个本来没人会给的答案。这是窗口被接受的代价，而窗口就是旋钮：想让桌面更早看到的部署把 `DSH_REMOTE_BRIDGE_OFFLINE_CLAIM_TTL_MS` 调小。

没有 APNs 签名密钥的桥不认领任何东西，行为与今天一致：扣着一道无法通告的题是纯损失。

离线认领不喂锁屏卡片通道（`liveActivity.noteQuestion`）；让卡片为一道待答题亮起来属于第 29 节的工作，不在本次范围。

本条决策的线路可见半边写在客户端协议文档（iOS 仓的 `docs/protocol-v1.md`）第 32 节；那条记录拥有协议语义，本条拥有桥侧的理由。
