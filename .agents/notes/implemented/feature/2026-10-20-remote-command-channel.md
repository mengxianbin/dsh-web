# Agent Note: Put the host's slash commands and skills on the remote bridge

Status: implemented

Channel note of [the protocol note](../architecture/2026-10-16-remote-bridge-protocol-v1.md), which owns the surface itself: the envelope, the pairing gate and the in-process gateway consume. This note owns one addition to that surface.

## Problem

A phone driving a session through `dsh-remote-bridge` could prompt, interrupt, read history and answer approvals, but it could not do what the desktop composer does with a leading slash: list the commands and skills the host offers that session, and run one of them. Protocol v1 had no method that read `ctx.commands`' effective view or the session-addressed skill catalog, and no way to ask the host whether a draft line resolves at all. The gap showed up twice — the phone could offer no directory, and a user who typed `/compact` had to send it as prompt text, where the host reads it as a message rather than as the command it is.

## Decision

- **A new capability, `commands.v1`, carries two methods.** `session.commands {sessionId}` answers `{sessionId, items:[{name, description, kind, line}]}` and `session.command {sessionId, line}` answers `{matched}`. Both are gated exactly like `agents.v1` and `session.fork.v1`: a client that does not declare the capability is refused `unknown-method` before the pairing gate and costs the host no gateway call, an unpaired client is refused `unpaired`, and the capability is advertised in `hello`'s `capabilities` so a client learns the channel exists without trying it.
- **The directory is two host catalogs folded into one flat list, read live on every call.** `commands/list` is the registry's effective view for that Agent (an Agent-scoped child's registration shadows the global one) and `skills/list` is the catalog that session's cwd and preset select. Every command comes first and every skill after, each in the host's own order. Nothing is cached across frames, nothing is paged and nothing is pushed: the bridge holds no index of what a session can run, so a command a plugin registered a moment ago and a skill a changed preset withdrew are both in the next answer, and there is no second source of truth to go stale.
- **`line` is the whole draft text, separator space included.** Both kinds answer `/<name> `, which is what the official composers insert, and the trailing space is required rather than cosmetic: both host surfaces resolve a bare gesture only when whitespace or the end of the text follows the name. A skill's line is therefore prompt text the host reads out of the submitted message, never a registry entry.
- **`matched` is the host's own resolution, reported and not re-derived.** `session.command` sends the line verbatim to `commands/execute` with an empty `submittedAttachments`, and answers `matched: true` only when the call returns a settled execution. The host answers `undefined` for both admission misses — a line its parser rejects, and a name its registry does not hold — so the bridge never decides what a line means, never pre-judges a command, and never refuses a line it does not recognise.
- **A host without these endpoints answers this bridge's own code.** `commands-unavailable` is raised when the gateway reports `invocation-unavailable` or `definition-unavailable`, which is its way of saying no active Remote method exports the endpoint. A service that is merely still activating keeps `gateway/service-unavailable`: that window is retried before it arrives, so a persisted failure is a broken deployment rather than an absent channel, and folding the two would hide it.
- **`hello` answers `minor:12`.** The command channel puts a new reply body on the wire, which is what this repository raises the minor for; `commands.v1` is appended as the fourteenth served capability.

## First-hand anchors in the installed CLI

- `CommandRuntime.execute` (`@deepseek-ai/dsh-commands` `lib/index.js`) returns `undefined` twice before any handler runs: `const parsed = parseCommand(line); if (parsed === void 0) return void 0;` and `const command = this.view(agent).get(parsed.name); if (command === void 0) return void 0;`. That pair is the whole `matched` vocabulary.
- The registry holds only what plugins register: `compact`, `feedback`, `goal`, `permission`, `plan` and `export` in this cohort, one `ctx.commands.register` per owning plugin. No `dsh-skill`, `dsh-skill-filesystem` or `dsh-tool-skill` calls it at all, so a skill name resolves through `parseCommand` and then misses the registry: `/adversarial-acceptance ` is a well-formed command line the host resolves to nothing.
- A skill is invoked by a gesture in user text: `SKILL_GESTURE = /(^|\s)\/([a-z0-9]+(?:-[a-z0-9]+)*)(?=\s|$)/` (`@deepseek-ai/dsh-tool-skill` `lib/index.js`), consumed by `invokedSkillNames` over `source.kind === 'user'` blocks before the step, and the official composer's `onPick` answers `\`/\${candidate.name} \`` (`@deepseek-ai/dsh-client-ui-skill` `lib/client.js`). The lookahead is why the bridge's line carries the space.
- Wire layouts come from the typert host descriptors, not from memory: `commands/list` takes `{agentId}`, `commands/execute` takes `{agentId, line, submittedAttachments}` with `agentId` as the agent-scope wire, and `skills/list` takes `{request: SkillListRequest}` where `SkillListRequest` is `{sessionId}`.

## Testing

`packages/dsh-remote-bridge/tests/commands.spec.ts` drives a real `BridgeConnection` over scriptable catalogs: the directory's order and its `kind`/`line` per row, both endpoints' wire arguments, a second listing paying for a second read, a row this bridge cannot render being dropped, `commands-unavailable` from each endpoint, an activation failure keeping its own code, `invalid-args` before any gateway call, `matched` on a hit and on each kind of miss, a host refusal crossing unchanged, the undeclared-capability path with zero gateway calls, the unpaired path, and the handshake announcement. The package suite runs 430 tests across 34 files and `tsgo --noEmit` is clean.

## Alternatives considered

- **Teach `session.prompt` to resolve a leading slash.** One method would then mean two things, and the bridge would become the judge of what a line is: the grammar, the Agent-scoped shadowing and the attachment admission would all move into it, while the host already appends `command/run` and `command/done` outside any turn — a lifecycle a prompt cannot reproduce. A client that wants a directory would still need a second method. Rejected.
- **Register every skill as a slash command on the bridge side.** It would make `/name` resolve, but it would also make the host log a `command/run` for an invocation the host never performed, and it would put a catalog the host owns into this bridge's registration table, where a preset change or a withdrawn skill has no way to reach it. Rejected: the honest answer for a skill line is `matched: false`, because the host resolves nothing.
- **Judge a line in the bridge to decide `matched` without calling the host.** Duplicating `parseCommand` and the scoped lookup would be a second grammar that drifts, and it would still be wrong whenever a preset adds a command the bridge has never seen. Rejected.
- **Subscribe `commands/change` and push a directory event.** The registry notification is global and unfiltered while a directory is per-session and scope-resolved, so a change frame could not say whose directory moved; a phone would still need a session-addressed answer, which is the call this method already is. Rejected: no event, no broadcast, read on demand.
- **Page the directory or cap its rows.** The registry is bounded by how many plugins register a command (six here plus client contributions) and the skill catalog is one preset's worth; a cursor over that list would be paid for by every answer and used by none. Rejected.
- **Answer `matched: true` for any syntactically valid slash line** so that a client could treat "the line looks like a command" as success. It would tell a phone that `/adversarial-acceptance` ran when nothing ran, which is the one thing this method exists to say truthfully. Rejected.
- **Keep `minor` at 11** and rely on the capability name alone. The capability is an announcement about behaviour, but the reply body is new on the wire, and this repository raises the minor for exactly that; leaving it would make two different protocol shapes claim one version. Rejected.

## Consequences

- A phone can list what a session can run and run one of it, with the host's own answer deciding whether anything happened.
- The bridge gives up knowing what a command *is*. It cannot tell a client which commands take free-form input, which accept attachments, or whether a name exists before running it — `CommandDescriptor.input` and `CommandDefinition` stay host vocabulary, and the directory forwards only `name` and `description`. A client that wants the input hint needs a further key and a further decision.
- Running a line has the command's own effects, `/compact` included: the method is a dispatch, not a probe. The only way to learn that a line will not run is to send it, and that costs one gateway call which logs nothing (the host records lifecycle events only after admission).
- Attachments are out of scope by construction: a draft line carries none, so the bridge sends an empty `submittedAttachments` and a command that requires attachments is reachable only from a composer that can stage them.
- A host that does not export the endpoints is told apart from one that refuses a call, so a client can disable the directory instead of retrying a call that cannot succeed.
- Not verified here: an end-to-end round trip against a running host process. The channel is covered by the package suite against a scriptable gateway, and the running host serves the new methods only after this package is rebuilt and the DSH process restarts.
